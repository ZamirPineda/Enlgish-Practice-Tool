Arquitectura Basada en el Espacio

La Arquitectura Basada en el Espacio (Space-Based Architecture - SBA) es un patrón de arquitectura de software diseñado para lograr una escalabilidad masiva, alta disponibilidad y un alto rendimiento al eliminar los cuellos de botella de la base de datos y la comunicación en red. Lo logra distribuyendo el procesamiento y los datos en memoria a través de una red de servidores, creando un "espacio" de datos compartido y transaccional.

---

Conceptos Principales

1. El "Espacio" (The Space)

El corazón de la SBA es el "Espacio", que es una representación de una Grid de Datos en Memoria (In-Memory Data Grid - IMDG) distribuida y transaccional.

  • Almacenamiento en Memoria: Los objetos de la aplicación se almacenan directamente en la memoria RAM de los nodos de la red, en lugar de una base de datos tradicional en disco.
  • Lógico y Distribuido: Aunque es una única entidad lógica, el Espacio está físicamente distribuido y replicado entre múltiples nodos.
  • Acceso Transaccional: Proporciona una API para leer, escribir, actualizar y eliminar objetos de forma transaccional, garantizando la consistencia de los datos dentro del Espacio.
  • Co-localización de Datos y Lógica: El diseño fundamental busca co-localizar los datos con la lógica de negocio que los procesa, minimizando la latencia de red.

2. Unidades de Procesamiento (Processing Units)

Son los componentes principales que ejecutan la lógica de negocio de la aplicación.

  • Contenedores Autocontenidos: Cada unidad de procesamiento contiene una parte del Espacio (datos), la lógica de negocio que opera sobre esos datos, y un servidor web (si es necesario).
  • Aislamiento: Son independientes entre sí y pueden desplegarse y escalarse de forma aislada.
  • Escalabilidad: Al añadir más unidades de procesamiento, se incrementa tanto la capacidad de procesamiento como la capacidad de almacenamiento del Espacio.

3. Grid de Datos en Memoria (In-Memory Data Grid - IMDG)

El Espacio implementa una IMDG que gestiona la distribución, replicación y consistencia de los datos en memoria.

  • Distribución: Fragmenta los datos del Espacio entre las distintas unidades de procesamiento.
  • Replicación: Replica los datos para proporcionar alta disponibilidad y tolerancia a fallos. Si una unidad falla, sus datos están disponibles en otra unidad.
  • Consistencia: Asegura que las operaciones sobre el Espacio sean consistentes, a menudo usando mecanismos como la replicación sincrónica o asincrónica.

4. Persistencia Asincrónica

Mientras que los datos residen principalmente en memoria, la SBA no ignora la necesidad de persistencia a largo plazo.

  • Escritura Diferida (Write-Behind): Los cambios en el Espacio se persisten a un almacén de datos tradicional (base de datos relacional, NoSQL, etc.) de forma asincrónica. Esto evita que la base de datos se convierta en un cuello de botella para las operaciones de lectura/escritura de alta frecuencia.
  • Durabilidad: Asegura que los datos no se pierdan completamente en caso de un fallo masivo del sistema que vacíe la memoria de todos los nodos.

5. Escalabilidad Elástica

El patrón está diseñado para una escalabilidad horizontal y elástica.

  • Añadir Nodos: Se pueden añadir o eliminar unidades de procesamiento dinámicamente según la demanda. Cuando se añade un nodo, el Espacio redistribuye automáticamente los datos y la carga de trabajo.
  • Autogestión: Muchos productos de SBA ofrecen capacidades de autodescubrimiento y autogestión para manejar la topología de la grid.

---

Ventajas

  • Alta Escalabilidad: Permite escalar la aplicación a miles de transacciones por segundo al añadir más unidades de procesamiento, sin un límite superior teórico impuesto por una base de datos centralizada.
  • Alto Rendimiento: Las operaciones se realizan en memoria, lo que reduce drásticamente la latencia en comparación con el acceso a disco. La co-localización de datos y lógica elimina las costosas llamadas a la red a una base de datos externa.
  • Alta Disponibilidad y Tolerancia a Fallos: La replicación de datos en el Espacio asegura que, si una unidad de procesamiento falla, otra unidad tiene una copia de los datos y puede asumir la carga sin interrupciones.
  • Baja Latencia: Ideal para aplicaciones que requieren respuestas en milisegundos o menos, como sistemas de comercio, juegos en línea, o análisis en tiempo real.
  • Resiliencia: El aislamiento de las unidades de procesamiento y la replicación de datos hacen que el sistema sea más robusto frente a fallos parciales.
  • Eliminación del Cuello de Botella de la Base de Datos: Libera a la base de datos de manejar todas las operaciones de lectura/escritura de alto volumen, permitiéndole centrarse en la persistencia a largo plazo y la integridad referencial.

---

Desventajas

  • Alto Consumo de Memoria y Costo: Almacenar todos o la mayoría de los datos en memoria requiere una gran cantidad de RAM, lo cual puede ser costoso, especialmente para conjuntos de datos muy grandes.
  • Complejidad de Gestión y Operación: La gestión de una grid de datos distribuida y un clúster de unidades de procesamiento es inherentemente más compleja que la gestión de una aplicación monolítica con una base de datos central. Requiere herramientas de monitoreo, despliegue y gestión más sofisticadas.
  • Curva de Aprendizaje: Los desarrolladores deben familiarizarse con los conceptos de sistemas distribuidos, transacciones distribuidas y la API específica del Espacio.
  • Persistencia Asincrónica y Consistencia: Aunque es una ventaja para el rendimiento, la persistencia asincrónica significa que, en un escenario de fallo catastrófico (pérdida de todos los nodos del clúster antes de que los datos se hayan persistido), podría haber una pequeña ventana de pérdida de datos. Requiere una cuidadosa consideración de la consistencia eventual.
  • No para Todos los Casos: No es el patrón adecuado para aplicaciones con conjuntos de datos gigantescos que no caben en memoria o para sistemas donde la latencia no es una preocupación crítica y la simplicidad de una base de datos tradicional es suficiente.
  • Dependencia del Proveedor: A menudo, se depende de productos IMDG comerciales o de código abierto específicos, lo que puede introducir un acoplamiento tecnológico.

Arquitectura Basada en el Espacio (SBA) en la Práctica: Una Plataforma de E-commerce de Venta Flash

Introducción a la Arquitectura Basada en el Espacio (SBA)

La Arquitectura Basada en el Espacio (SBA), también conocida como "Grid de Datos en Memoria" (In-Memory Data Grid - IMDG), es un patrón de arquitectura distribuida diseñado para lograr una escalabilidad masiva y una alta disponibilidad, especialmente bajo cargas de trabajo impredecibles y picos de tráfico extremos. Su principio central es la replicación de datos en memoria a través de múltiples "espacios" (IMDGs) que son co-ubicados con las unidades de procesamiento (servicios) que los necesitan. Esto elimina el cuello de botella tradicional de una base de datos centralizada y permite que el sistema escale linealmente añadiendo más nodos de procesamiento.

Escenario Empresarial: "MegaOfertas.com"

Empresa: MegaOfertas.com

Sector: E-commerce

Problema Central: Gestión de Picos de Demanda Extremos en Ventas Flash y Lanzamientos de Productos Limitados.

MegaOfertas.com es una popular plataforma de e-commerce conocida por sus "ventas flash" altamente anticipadas y lanzamientos exclusivos de productos con stock limitado (por ejemplo, entradas para conciertos muy demandados, ediciones especiales de videojuegos, ofertas de "Black Friday"). Estas ventas a menudo generan un tráfico de usuarios masivo y simultáneo, con millones de intentos de acceso y compra en cuestión de minutos.

#### El Problema que Enfrentaba MegaOfertas.com

Antes de adoptar SBA, MegaOfertas.com operaba con una arquitectura monolítica (o un conjunto de microservicios acoplados) que se apoyaba en una base de datos relacional centralizada (por ejemplo, PostgreSQL o MySQL) para gestionar el inventario, pedidos, sesiones de usuario, etc.

Los problemas recurrentes eran los siguientes:

1. Cuello de Botella de la Base de Datos: Durante los picos de ventas flash, la base de datos relacional era el punto de fallo y el principal cuello de botella. La enorme cantidad de lecturas (consultas de stock, datos de productos) y escrituras (actualizaciones de stock, creación de pedidos, sesiones de usuario) simultáneas agotaba los recursos de la base de datos (CPU, I/O de disco, conexiones).

2. Degradación del Rendimiento y Tiempos de Espera: Las páginas se cargaban lentamente, las operaciones de añadir al carrito tardaban en responder y las confirmaciones de compra fallaban o tomaban minutos, frustrando a los usuarios y resultando en abandonos.

3. Caídas del Sistema y Pérdida de Ingresos: En varias ocasiones, la base de datos se colapsó por completo, dejando el sitio web inaccesible durante eventos críticos de venta, lo que se traducía en pérdidas millonarias y un daño severo a la reputación de la marca.

4. Escalabilidad Costosa y Compleja: Intentar escalar la base de datos implicaba soluciones caras (hardware de alta gama, sharding manual, réplicas de lectura complejas) que eran difíciles de implementar, mantener y aún así no garantizaban el rendimiento bajo cargas extremas.

5. Experiencia de Usuario Pobre: Los usuarios experimentaban mensajes de error constantes, artículos "desaparecidos" del carrito o la incapacidad de completar una compra, lo que llevaba a una gran insatisfacción y quejas en redes sociales.

Implementación de la Arquitectura Basada en el Espacio (SBA)

Para abordar estos desafíos, MegaOfertas.com decidió rediseñar su arquitectura crítica para las ventas flash utilizando el patrón SBA.

#### Componentes Clave de la Implementación:

1. Unidades de Procesamiento (PUs):

  • * La aplicación se dividió en microservicios o "unidades de procesamiento" (PUs) independientes, cada una con una responsabilidad bien definida (ej. PU_GestionStock, PU_ProcesamientoPedidos, PU_SesionesUsuario).
  • Crucialmente, cada PU no solo contenía la lógica de negocio, sino también su propio "espacio" (IMDG) para almacenar y gestionar los datos relevantes* que necesitaba.

2. Los "Espacios" (Grids de Datos en Memoria - IMDG):

  • * En lugar de una única base de datos central, los datos clave se replicaron y distribuyeron en múltiples "espacios" de datos en memoria.
  • *SpaceStockProducto: Para cada producto en una venta flash, su nivel de stock actual se cargaba y replicaba en este espacio a través de múltiples PUs de PU_GestionStock. Las operaciones de reserva y decremento de stock se realizaban directamente en memoria, lo que era increíblemente rápido.
  • *SpacePedidosPendientes: Los datos de pedidos recién creados se almacenaban aquí temporalmente mientras esperaban confirmación de pago.
  • *SpaceSesionesUsuario: La información de la sesión de cada usuario (carrito de compra, estado de inicio de sesión) se guardaba en este espacio distribuido, permitiendo failover transparente y acceso rápido.
  • * Estos espacios eran gestionados por tecnologías como Apache Ignite, Hazelcast o GigaSpaces, configuradas para replicar automáticamente los datos entre los nodos de procesamiento.

3. Mecanismos de Comunicación y Sincronización:

  • * Comunicación Síncrona Limitada: Las operaciones críticas de lectura/escritura (como reservar stock o añadir al carrito) se realizaban localmente dentro de la PU y su espacio co-ubicado para maximizar el rendimiento.
  • * Colas de Mensajes Asíncronas (Kafka/RabbitMQ): Para la consistencia eventual y la integración con sistemas legados o menos críticos:
  • * Cuando se realizaba un cambio en un espacio (ej. decremento de stock por una reserva), un evento se publicaba en una cola de mensajes.
  • * Otros PUs o sistemas (ej. sistema de informes, base de datos persistente para auditoría) se suscribían a estos eventos para actualizar su propia vista de los datos, garantizando una consistencia eventual.
  • * Por ejemplo, después de una venta flash, el stock final se consolidaba y persistía en la base de datos relacional tradicional para auditoría y gestión a largo plazo.

4. Orquestación y Despliegue (Kubernetes/Docker):

  • * Las PUs se empaquetaron en contenedores Docker y se orquestaron usando Kubernetes.
  • * Esto permitió escalar horizontalmente las PU_GestionStock, PU_ProcesamientoPedidos y otras PUs en cuestión de segundos, simplemente añadiendo más pods de Kubernetes a medida que aumentaba el tráfico.
  • * El balanceador de carga de Kubernetes (Ingress) distribuía las solicitudes entrantes entre las instancias disponibles de las PUs.

#### Flujo de Operación Durante una Venta Flash:

1. Pre-Carga: Horas antes de la venta flash, los datos críticos (stock inicial de los productos en oferta, precios, descripciones abreviadas) se cargaban desde la base de datos persistente hacia los SpaceStockProducto y otros espacios relevantes en memoria, a través de todas las PUs activas.

2. Acceso del Usuario: Cuando un usuario navegaba por la oferta, su solicitud era dirigida a una PU_GestionStock disponible. Las consultas de stock y descripción de producto se resolvían directamente desde el SpaceStockProducto local en memoria, con latencia mínima.

3. Añadir al Carrito / Reserva de Stock: Cuando un usuario intentaba añadir un artículo al carrito, la PU_GestionStock realizaba una operación de "reserva" atómica en su SpaceStockProducto local. Esta reserva era extremadamente rápida. Si la reserva era exitosa, el stock disponible se decrementaba inmediatamente en ese espacio, y un evento asíncrono se publicaba para replicar el cambio a otros espacios y, eventualmente, a la base de datos persistente para fines de auditoría.

4. Procesamiento de Pedidos: Una vez que el usuario confirmaba la compra, la PU_ProcesamientoPedidos creaba un objeto PedidoPendiente en su SpacePedidosPendientes. Esto iniciaba un flujo asíncrono para procesar el pago y consolidar el pedido final.

5. Sesiones de Usuario: Las interacciones del usuario (elementos en el carrito, estado de login) se mantenían en el SpaceSesionesUsuario, asegurando que la información de la sesión fuera persistente incluso si el servidor al que estaban conectados fallaba.

Resultados y Beneficios Obtenidos por MegaOfertas.com

La implementación de la Arquitectura Basada en el Espacio transformó por completo la capacidad de MegaOfertas.com para gestionar eventos de alta demanda:

1. Escalabilidad Masiva Comprobada: La plataforma pudo escalar horizontalmente para manejar más de 50 veces el tráfico pico anterior, procesando millones de transacciones por minuto sin degradación del rendimiento. Esto se logró simplemente añadiendo más servidores (o pods en Kubernetes) que ejecutaban las PUs y sus espacios.

2. Rendimiento Extremo: Los tiempos de respuesta para las operaciones críticas (consulta de stock, añadir al carrito, confirmación de reserva) se redujeron a milisegundos. Las páginas se cargaban instantáneamente.

3. Alta Disponibilidad y Resiliencia: No hubo un único punto de fallo. Si un servidor o una instancia de PU fallaba, otras instancias con datos replicados se hacían cargo sin interrupción, garantizando un tiempo de actividad del 99.999%.

4. Reducción Drástica de Errores y Caídas: Las ventas flash se realizaban sin incidentes de rendimiento o caídas del sistema, lo que eliminó las pérdidas de ingresos asociadas a problemas técnicos.

5. Experiencia de Usuario Mejorada: Los clientes experimentaron un proceso de compra fluido y rápido, lo que aumentó la satisfacción, la fidelidad y la reputación de la marca. Las tasas de conversión en ventas flash mejoraron significativamente.

6. Eficiencia de Costos: Se pudo escalar los recursos bajo demanda para los eventos críticos y reducirlos rápidamente una vez finalizados, optimizando el uso de la infraestructura y reduciendo los costos operativos a largo plazo en comparación con el sobreaprovisionamiento constante de una base de datos centralizada.

7. Desarrollo Ágil: Al dividir la aplicación en PUs autónomas, los equipos de desarrollo podían trabajar de forma más independiente, acelerando el ciclo de vida de desarrollo y despliegue de nuevas características.

En resumen, la Arquitectura Basada en el Espacio permitió a MegaOfertas.com no solo resolver sus problemas de escalabilidad y rendimiento, sino también transformar la experiencia del cliente y consolidar su posición como líder en el mercado de ventas flash y ofertas exclusivas, capitalizando al máximo los eventos de alta demanda.

Preguntas de Entrevista

La Arquitectura Basada en el Espacio (SBA) es famosa por su escalabilidad lineal y alta disponibilidad. ¿Cómo logra estos atributos sin una base de datos centralizada, y cuáles son las implicaciones clave para la gestión de la consistencia de los datos en este modelo?

SBA logra escalabilidad y alta disponibilidad distribuyendo tanto los datos como la lógica de procesamiento en 'espacios' o unidades de procesamiento (PUs) independientes y auto-contenidas, que se replican y se ejecutan en múltiples nodos. Los datos se mantienen principalmente en memoria (IMDG - In-Memory Data Grid) dentro de cada PU o en un clúster de estas. La eliminación de la base de datos centralizada previene cuellos de botella y puntos únicos de fallo.Las implicaciones para la consistencia de datos son que SBA generalmente adopta un modelo de 'consistencia eventual' para los datos replicados a través de diferentes espacios. Aunque dentro de un espacio local (o una partición de datos), la consistencia puede ser fuerte, las actualizaciones que afectan a múltiples espacios o particiones pueden no ser instantáneamente visibles en todas partes. Esto requiere que los desarrolladores diseñen sistemas que sean tolerantes a la latencia de propagación de datos y que manejen la resolución de conflictos si es necesario, a menudo utilizando mecanismos como la replicación asíncrona o modelos de 'lectura propia' (Read Your Own Writes).

La implementación de una Arquitectura Basada en el Espacio (SBA) puede introducir complejidades, especialmente en la sincronización de datos y la integridad transaccional a través de múltiples unidades de procesamiento. Explica los principales desafíos asociados con estos aspectos y cómo se mitigan comúnmente.

Los principales desafíos son: 1. Sincronización de Datos: Cuando los datos se replican o particionan a través de múltiples PUs, mantener la coherencia y garantizar que todos los 'espacios' tengan la versión más reciente puede ser complejo, especialmente con escrituras concurrentes. 2. Integridad Transaccional Distribuida: Las transacciones que involucran datos dispersos en diferentes PUs son difíciles de lograr con garantías ACID fuertes (Atomicidad, Consistencia, Aislamiento, Durabilidad) sin reintroducir cuellos de botella (ej., transacciones de dos fases).Las mitigaciones comunes incluyen: Consistencia Eventual: Se acepta que los datos serán consistentes con el tiempo, pero no instantáneamente. Esto es adecuado para muchas aplicaciones web y móviles donde la disponibilidad es primordial. Patrones de Compensación: Para transacciones distribuidas, se utilizan sagas o patrones de compensación para deshacer acciones previas si una parte de la transacción falla, en lugar de un rollback atómico global. Particionamiento Inteligente: Diseñar la partición de datos para minimizar las transacciones entre particiones. Agrupar los datos relacionados en el mismo espacio o partición reduce la necesidad de sincronización distribuida. Mecanismos de Replicación: Utilizar replicación síncrona dentro de un grupo pequeño para alta disponibilidad, y asíncrona entre grupos para escalabilidad geográfica. * Optimistic Locking/Versioning: Para manejar conflictos de escritura, se pueden emplear técnicas de bloqueo optimista o control de versiones de datos.

Dada la naturaleza de la Arquitectura Basada en el Espacio, ¿en qué escenarios o tipos de aplicaciones *no* recomendarías su uso, y qué alternativa arquitectónica considerarías en su lugar, justificando tu elección?

No recomendaría una SBA en escenarios donde: 1. La consistencia de datos fuerte y en tiempo real es una prioridad absoluta y no negociable para todas las operaciones (ej., sistemas bancarios que requieren atomicidad a nivel de centavo en todas las transacciones, o sistemas de control industriales críticos donde la consistencia instantánea es vital para la seguridad). 2. El volumen de datos es extremadamente grande y excede la capacidad de la memoria RAM de un clúster razonable, y los patrones de acceso son predominantemente basados en disco con consultas complejas. 3. Los datos son predominantemente estáticos o se actualizan con poca frecuencia, ya que los beneficios de la alta capacidad de procesamiento y la baja latencia en memoria no se aprovecharían plenamente, y la complejidad operacional no se justificaría. 4. El presupuesto o la experiencia del equipo son limitados, ya que SBA requiere una experiencia significativa en sistemas distribuidos, gestión de consistencia eventual y operaciones.En estos casos, consideraría alternativas como: Arquitectura de Microservicios con bases de datos políglotas: Permite a cada servicio elegir la base de datos más adecuada para sus necesidades, logrando consistencia fuerte donde sea necesario y consistencia eventual en otros lugares. Arquitectura Monolítica (para aplicaciones menos exigentes): Si la escalabilidad no es una preocupación principal y la consistencia fuerte es clave, un monolito bien diseñado con una base de datos relacional tradicional podría ser más simple y económico de mantener. * Arquitectura Orientada a Eventos con una base de datos distribuida tradicional: Para un alto volumen de datos en disco y necesidad de consistencia transaccional en ciertos contextos, una base de datos como CockroachDB o Spanner podría ofrecer escalabilidad sin sacrificar tanta consistencia como un SBA.

En una Arquitectura Basada en el Espacio, el manejo de fallos y la recuperación son fundamentales para la alta disponibilidad. Describe cómo se abordan típicamente la gestión de la resiliencia y la recuperación de datos ante la caída de un nodo o de una unidad de procesamiento (PU) completa.

La resiliencia y la recuperación en SBA se basan principalmente en la redundancia y la replicación de datos: 1. Replicación de Datos: Los datos en cada partición del 'espacio' se replican síncrona o asincrónicamente en múltiples nodos. Si un nodo o PU que contiene la copia primaria falla, una copia secundaria (réplica) toma el relevo automáticamente, minimizando el tiempo de inactividad. Los sistemas SBA a menudo usan un esquema de replicación primario/secundario o quorum. 2. Monitoreo y Detección de Fallos: Se utilizan mecanismos robustos de monitoreo de latidos (heartbeats) y detección de fallos para identificar nodos o PUs caídos rápidamente. 3. Failover Automático: Cuando se detecta un fallo, el sistema realiza un proceso de failover automático. Esto implica que una de las réplicas secundarias es promovida a primaria, y los clientes se redirigen a la nueva primaria o a una PU de respaldo que contenga los datos. Esto es gestionado por un componente de orquestación o el propio IMDG. 4. Auto-Sanación (Self-Healing): Después de un failover, el sistema puede intentar auto-sanarse. Esto podría implicar provisionar un nuevo nodo o PU para reemplazar el fallido y luego replicar los datos necesarios para restaurar el nivel deseado de redundancia. 5. Persistencia: Aunque los datos están en memoria, los sistemas SBA a menudo tienen un mecanismo de persistencia en disco (ej., diario de transacciones o snapshots periódicos) para garantizar la durabilidad de los datos en caso de un fallo catastrófico que afecte a todas las réplicas de una partición, permitiendo la recuperación desde un estado consistente previo.

Una de las características distintivas de SBA es su dependencia de In-Memory Data Grids (IMDG). Discute el impacto de esta elección en la durabilidad y recuperación de datos, y detalla cómo se abordan estas preocupaciones en un sistema SBA de producción.

La dependencia de IMDG en SBA tiene un impacto significativo en la durabilidad y recuperación: 1. Durabilidad: Por naturaleza, los datos en memoria son volátiles. Si un nodo falla y los datos no han sido persistidos o replicados, se pierden. Esto contrasta con las bases de datos tradicionales que persisten los datos en disco de forma predeterminada. 2. Recuperación: La recuperación de datos después de un fallo puede ser más rápida que en sistemas basados en disco debido a que los datos están en RAM, pero el proceso de reconstruir el estado de un espacio a partir de réplicas o logs requiere una gestión cuidadosa.En producción, estas preocupaciones se abordan de varias maneras: Replicación Robusta: Esta es la mitigación primaria. Los datos se replican en tiempo real o casi real en múltiples nodos. Si un nodo falla, una réplica asume su rol, garantizando que los datos no se pierdan y la disponibilidad se mantenga. Persistencia Asíncrona a Disco: Aunque los datos están en memoria para operaciones rápidas, se suelen escribir asincrónicamente a un almacenamiento persistente (ej., un archivo de registro de transacciones o una base de datos secundaria). Esto asegura que, en un escenario de fallo total (donde todas las réplicas fallan), los datos puedan recuperarse desde la última copia persistida. Snapshots y Puntos de Verificación: Se toman instantáneas periódicas de los datos en memoria y se persisten en disco. Esto reduce el tiempo de recuperación al no tener que aplicar un largo historial de transacciones desde cero. Write-Behind / Write-Through Caching: Algunos IMDG ofrecen modos de escritura que sincronizan los cambios con una base de datos persistente subyacente de forma asíncrona (write-behind) o síncrona (write-through) para asegurar la durabilidad mientras se mantiene la velocidad de lectura/escritura en memoria. * Diseño de Aplicación Tolerante a Fallos: La aplicación misma debe estar diseñada para ser consciente de la consistencia eventual y capaz de reintentar operaciones o gestionar estados temporales en caso de interrupciones.
