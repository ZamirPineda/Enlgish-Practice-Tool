Evolución de Java (8, 11, 17+)

Aquí tienes una explicación del patrón "Evolución de Java (8, 11, 17+)", presentado como una estrategia o patrón de gestión de plataforma dentro de una arquitectura de software.

# Evolución de Java (8, 11, 17+)

Aunque no es un "patrón de arquitectura de software" en el sentido tradicional (como Microservicios o Capas), "Evolución de Java (8, 11, 17+)" se refiere a la estrategia arquitectónica y de gestión de ciclo de vida para mantener las aplicaciones Java actualizadas con las versiones de la plataforma. Implica la decisión consciente de migrar progresivamente entre las versiones de Soporte a Largo Plazo (LTS - Long-Term Support) de Java, en lugar de permanecer indefinidamente en una versión antigua o adoptar cada nueva versión. El patrón se centra en la adopción de las versiones LTS clave: Java 8 (el estándar anterior), Java 11 (la primera LTS post-Jigsaw), Java 17 (la actual LTS), y las futuras LTS como Java 21+.

Conceptos Principales

Ciclo de Lanzamiento

Oracle y la comunidad Java adoptaron un nuevo ciclo de lanzamientos semestral a partir de Java 9. Esto significa que cada seis meses se publica una nueva versión de Java (ej. Java 9, 10, 12, 13, etc.), trayendo nuevas características y mejoras. Este ciclo acelera la entrega de innovaciones pero requiere una estrategia clara para la adopción en entornos de producción.

Versiones LTS (Long-Term Support)

Son versiones específicas del JDK que reciben un soporte extendido (actualizaciones de seguridad, correcciones de errores) por parte de Oracle y otros proveedores de JDK, generalmente durante varios años.

  • Java 8: Lanzada en 2014, fue la LTS dominante durante muchos años. Introdujo Streams, Lambdas y nuevas APIs de Fecha/Hora.
  • Java 11: Lanzada en 2018, la primera LTS importante después de Java 8 y la introducción del sistema de módulos (Jigsaw) en Java 9. Trajo var para variables locales, nuevos recolectores de basura, y mejoras en HTTP/2.
  • Java 17: Lanzada en 2021, la actual LTS. Continúa con mejoras de rendimiento, nuevas características del lenguaje (ej. Records, Text Blocks, Sealed Classes), y avances en la JVM.
  • Java 21: Lanzada en 2023, la próxima LTS.

El patrón "Evolución de Java" se centra principalmente en la migración de una versión LTS a la siguiente.

Versiones No-LTS / Feature Releases

Son las versiones intermedias que se liberan cada seis meses entre las versiones LTS (ej. Java 9, 10, 12, 13, 14, 15, 16, 18, 19, 20). Estas versiones tienen un ciclo de soporte muy corto (6 meses, hasta el siguiente lanzamiento) y no se recomiendan para entornos de producción a largo plazo. Su propósito es introducir y probar nuevas características que eventualmente madurarán en una futura versión LTS.

Migración Incremental

La idea central de este "patrón" es realizar actualizaciones de Java de manera incremental y planificada, saltando de una versión LTS a la siguiente (ej. de 8 a 11, luego de 11 a 17, etc.). Esto contrasta con:

1. Permanecer en una versión antigua indefinidamente: Acumula deuda técnica, riesgo de seguridad y pérdida de beneficios de rendimiento y nuevas características.

2. Adoptar cada versión semestral: Implica un esfuerzo de actualización constante y alto riesgo debido al corto ciclo de soporte de las versiones no-LTS.

La migración incremental busca un equilibrio, permitiendo aprovechar las mejoras de la plataforma de forma controlada y con soporte a largo plazo.

Ventajas

  • Rendimiento Mejorado: Cada nueva versión de Java y la JVM trae optimizaciones significativas en el rendimiento de la aplicación, el uso de memoria y la eficiencia del recolector de basura.
  • Nuevas Características del Lenguaje: Acceso a construcciones modernas del lenguaje (ej. var, Records, Text Blocks, Switch Expressions, Sealed Classes) que mejoran la productividad del desarrollador, la legibilidad del código y reducen el boilerplate.
  • Seguridad Mejorada: Las versiones LTS reciben parches de seguridad continuos. Las versiones más recientes también deprecian y eliminan APIs inseguras o poco eficientes.
  • Mejor Mantenibilidad: Código más limpio, conciso y expresivo gracias a las nuevas características, lo que facilita el mantenimiento y la evolución.
  • Acceso a Bibliotecas y Frameworks Modernos: Muchos frameworks y bibliotecas populares (Spring Boot, Kafka, etc.) requieren o se optimizan para versiones más recientes de Java, o directamente dejan de soportar versiones muy antiguas.
  • Soporte de la Comunidad y del Ecosistema: Es más fácil encontrar soporte, herramientas y soluciones para versiones modernas y activamente mantenidas de Java.
  • Atracción de Talento: Los desarrolladores suelen preferir trabajar con tecnologías y versiones de lenguaje actuales.

Desventajas

  • Esfuerzo de Migración: La migración de una LTS a otra puede requerir un esfuerzo considerable:
  • * Cambios en el Código: Aunque la retrocompatibilidad es una prioridad, pueden surgir cambios en APIs, deprecaciones o eliminaciones de funcionalidades.
  • * Sistema de Módulos (Jigsaw): La transición de Java 8 a Java 11 (y posteriores) implica lidiar con el sistema de módulos, lo que puede requerir ajustes significativos en las dependencias y la estructura del proyecto.
  • * Actualización de Dependencias: Bibliotecas de terceros, frameworks y herramientas de construcción (Maven, Gradle) deben ser compatibles con la nueva versión de Java.
  • * Cambios en la Configuración del Build: Las herramientas de CI/CD, scripts de build y configuraciones de entorno necesitan ser actualizadas.
  • Riesgos de Compatibilidad: Potenciales "breaking changes" que pueden afectar el comportamiento de la aplicación, especialmente si se dependía de APIs internas o comportamientos no especificados.
  • Curva de Aprendizaje: Los desarrolladores deben familiarizarse con las nuevas características del lenguaje y las mejores prácticas asociadas a la versión más reciente.
  • Costos Operacionales: Aparte del esfuerzo de desarrollo, se requiere tiempo para pruebas exhaustivas, despliegue y monitoreo para asegurar la estabilidad en el nuevo entorno de Java.
  • Fragmentación Interna: En organizaciones con múltiples aplicaciones, algunas pueden permanecer en versiones antiguas, creando un ecosistema heterogéneo que puede ser difícil de gestionar.
  • Disponibilidad de JDKs: Aunque hay muchas opciones (OpenJDK, Adoptium, Azul Zulu, Amazon Corretto, etc.), el soporte comercial y gratuito puede variar entre versiones y proveedores.

Ejemplo de Aplicación Real

El concepto de "Evolución de Java (8, 11, 17+)" se refiere a la estrategia de una organización para migrar y mantener sus aplicaciones Java actualizadas a versiones más recientes y soportadas del lenguaje y la plataforma, aprovechando las mejoras en rendimiento, seguridad y características de desarrollo que cada versión LTS (Long-Term Support) ofrece. No se trata de una única migración, sino de un plan continuo para mantenerse al día con el ecosistema Java.

Ejemplo Detallado: Evolución del Sistema Core de un Banco Regional

1. Problema que la Empresa Enfrentaba

Nombre de la Empresa: Banco del Sol (un banco regional con operaciones de tamaño medio).

Sistema Crítico: El "Sistema Central de Gestión de Préstamos (SCGP)", una aplicación monolítica encargada de la originación, administración y seguimiento de todos los préstamos bancarios (hipotecarios, personales, empresariales). Este sistema era el corazón de las operaciones de crédito del banco.

Situación Inicial:

El SCGP estaba desarrollado en Java 8 (Oracle JDK 8) y desplegado en servidores de aplicaciones tradicionales (JBoss EAP 6.x) en un centro de datos on-premise. Había estado en producción durante más de 10 años, con mantenimiento incremental pero sin una actualización significativa de su plataforma subyacente.

Problemas Específicos:

1. Seguridad y Cumplimiento:

  • * Java 8 había alcanzado el fin de su soporte público gratuito, lo que implicaba una falta de parches de seguridad para nuevas vulnerabilidades a menos que se pagara por un soporte comercial extendido (que era costoso).
  • * Las auditorías de seguridad y cumplimiento normativo (financiero, GDPR local) señalaban la plataforma obsoleta como un riesgo significativo.

2. Rendimiento y Escalabilidad:

  • * El SCGP experimentaba picos de carga durante los procesos de cierre de mes o campañas de lanzamiento de préstamos, resultando en latencia y tiempos de respuesta lentos para los usuarios y sistemas integrados.
  • * La JVM de Java 8 no contaba con las optimizaciones de rendimiento y los recolectores de basura más eficientes introducidos en versiones posteriores, lo que limitaba el uso eficiente de los recursos del servidor.

3. Productividad del Desarrollador y Costo de Mantenimiento:

  • * El equipo de desarrollo se sentía frustrado por la necesidad de trabajar con un stack tecnológico desactualizado. La falta de características de lenguaje modernas de Java (como var, records, switch expressions, etc.) hacía el código más verboso y propenso a errores.
  • * Era difícil atraer y retener talento joven que buscaba trabajar con tecnologías más actuales.
  • * Las herramientas de desarrollo (IDEs, frameworks) tenían un soporte limitado o descontinuado para Java 8, complicando el desarrollo y la depuración.
  • * Los costos de licencia del JDK comercial para Java 8 eran una carga creciente.

4. Innovación y Adopción Cloud:

  • * El banco quería explorar la migración a la nube y la adopción de arquitecturas de microservicios, pero el SCGP monolítico en Java 8 era una barrera significativa para estas iniciativas. La integración con nuevas APIs y servicios modernos era compleja.

2. Implementación del Concepto "Evolución de Java"

El Banco del Sol adoptó una estrategia de "Evolución de Java" en fases, centrándose en las versiones LTS (Long-Term Support) para garantizar estabilidad y soporte a largo plazo.

#### Fase 1: Preparación y Migración a Java 11 (LTS)

1. Análisis Exhaustivo: Un equipo multidisciplinario (desarrollo, operaciones, seguridad) realizó un análisis de dependencias (librerías de terceros, APIs internas), identificando incompatibilidades potenciales con Java 11. Se utilizaron herramientas de análisis estático y de migración.

2. Modernización de Dependencias: Se actualizaron todas las librerías y frameworks (Spring Framework, Hibernate, Apache Commons) a versiones compatibles con Java 11. Esto fue un esfuerzo significativo, ya que algunas librerías requerían refactorización de código.

3. Abordaje de Cambios Rompedores (Java 9, 10, 11):

  • * Módulo Java Platform (JPMS): Aunque no se modularizó completamente el SCGP de inmediato, se aseguró que la aplicación funcionara correctamente con el nuevo sistema de módulos, ajustando el classpath y resolviendo dependencias implícitas.
  • * Eliminación de JAXB/JAX-WS: Dado que estas APIs fueron desacopladas del JDK en Java 11, se añadieron como dependencias explícitas de Maven/Gradle para mantener la funcionalidad de XML y servicios web SOAP.
  • * Otros Cambios: Se refactorizaron usos internos de APIs Sun que ya no estaban disponibles o se movieron.

4. Actualización de Servidor de Aplicaciones y Despliegue: Se migró de JBoss EAP 6.x a JBoss EAP 7.x (compatible con Java 11). Se comenzó a experimentar con la containerización de componentes en Docker.

5. Pruebas Rigurosas: Se realizaron pruebas unitarias, de integración, de rendimiento y de seguridad exhaustivas para garantizar la estabilidad y funcionalidad del SCGP en Java 11.

6. Adopción de OpenJDK: El banco cambió de Oracle JDK a una distribución de OpenJDK (Eclipse Adoptium) para eliminar los costos de licencia.

#### Fase 2: Migración a Java 17 (LTS) y Estrategia Cloud-Native

1. Monitoreo y Optimización en Java 11: Durante el período en Java 11, se monitorizó el rendimiento y se identificaron cuellos de botella. Se aprovechó G1 como recolector de basura por defecto, mejorando la latencia.

2. Preparación para Java 17: Se repitió el proceso de análisis de dependencias y compatibilidad, centrándose en los cambios introducidos entre Java 11 y Java 17.

3. Aprovechamiento de Nuevas Características (Java 12-17):

  • * Se refactorizaron partes del código para usar switch expressions, text blocks, Records (para DTOs inmutables) y Pattern Matching for instanceof, mejorando la legibilidad y concisión.
  • * Se evaluó la posibilidad de usar Sealed Classes para modelar jerarquías de clases restringidas en nuevas funcionalidades del SCGP.

4. Estrategia Cloud-Native y Microservicios: La migración a Java 17 coincidió con una iniciativa para refactorizar los módulos más críticos del SCGP en microservicios basados en Spring Boot, desplegados en Kubernetes en una nube híbrida. Java 17, con sus mejoras en tiempo de inicio y uso de memoria, es más adecuado para entornos de contenedores.

5. Pipeline CI/CD Mejorado: Se establecieron pipelines de CI/CD robustos que podían compilar y probar la aplicación con diferentes versiones de Java, facilitando futuras actualizaciones.

#### Fase 3: Mantenimiento y Evolución Continua (Post-17)

1. Política de Actualización LTS: El banco estableció una política de actualizar a la siguiente versión LTS de Java tan pronto como sea práctica y económicamente viable (generalmente cada 2-3 años).

2. Capacitación Continua: Se invirtió en la capacitación de los desarrolladores en las últimas características de Java y prácticas de desarrollo moderno.

3. Monitoreo Proactivo: Implementación de herramientas de APM (Application Performance Monitoring) para detectar y resolver problemas de rendimiento o compatibilidad rápidamente después de cada actualización.

3. Resultados y Beneficios Obtenidos

La estrategia de evolución de Java trajo beneficios transformadores al Banco del Sol:

1. Seguridad Reforzada y Cumplimiento:

  • * El SCGP opera con las últimas características de seguridad de Java, minimizando el riesgo de vulnerabilidades conocidas.
  • * Las auditorías de seguridad ahora son más fluidas, y el banco cumple con los estándares regulatorios actuales, evitando multas y daños reputacionales.

2. Mejora Sustancial del Rendimiento:

  • * Reducción de Latencia: Los tiempos de respuesta del SCGP se redujeron en un 30-40% gracias a las optimizaciones de la JVM y los recolectores de basura de Java 11 y 17.
  • * Procesos Batch Más Rápidos: Los procesos de cierre de mes y cálculo de intereses se completan en la mitad del tiempo, liberando recursos y permitiendo operaciones más eficientes.
  • * Menores Costos de Infraestructura: El uso más eficiente de la CPU y la memoria por parte de las nuevas JVMs permitió al banco reducir el número de instancias de servidor o migrar a tipos de instancias más pequeños en la nube, resultando en un ahorro de costos de infraestructura del 15-20%.

3. Alta Productividad del Desarrollador y Reducción del Débito Técnico:

  • * Código Más Limpio y Conciso: El uso de var, Records, switch expressions y Text Blocks ha reducido la verbosidad del código en un 20%, haciéndolo más legible y fácil de mantener.
  • * Desarrollo Acelerado: Los desarrolladores pueden implementar nuevas características y corregir errores más rápidamente, utilizando herramientas y IDEs modernos con soporte completo.
  • * Atracción de Talento: La adopción de un stack tecnológico moderno ha mejorado la moral del equipo y ha facilitado la contratación de nuevos desarrolladores.

4. Reducción Significativa de Costos:

  • * Eliminación de Licencias: El cambio a OpenJDK eliminó por completo los costos de licencia de Java.
  • * Reducción de Mantenimiento: La menor cantidad de deuda técnica y la mayor estabilidad del sistema redujeron las horas dedicadas a mantenimiento correctivo.

5. Agilidad Empresarial e Innovación:

  • * Preparación para la Nube: La evolución de Java sentó las bases para la estrategia de migración a la nube del banco, permitiendo la refactorización a microservicios y el despliegue en Kubernetes.
  • * Integración Moderna: El SCGP puede integrarse de manera más sencilla y eficiente con nuevas APIs y servicios, permitiendo al banco lanzar nuevos productos financieros y características más rápidamente al mercado.
  • * Escalabilidad Mejorada: La arquitectura modular y el despliegue en contenedores permiten al SCGP escalar horizontalmente según la demanda, garantizando la continuidad del negocio durante picos de carga.

En resumen, la estrategia de "Evolución de Java" no fue simplemente una actualización técnica, sino una inversión estratégica que modernizó un sistema crítico, mejoró la seguridad, optimizó el rendimiento y transformó la capacidad del Banco del Sol para innovar y competir en el mercado financiero digital.

Preguntas de Entrevista

¿Cómo han transformado las características de programación funcional introducidas en Java 8 (Lambdas, Streams, Optional) el diseño arquitectónico de aplicaciones y los patrones de desarrollo, especialmente en sistemas de alto rendimiento? Discute las implicaciones de rendimiento y las mejores prácticas al integrar estos enfoques con los métodos imperativos tradicionales.

La programación funcional en Java 8 promovió un estilo de programación más declarativo, inmutable y conciso. Arquitectónicamente, facilita la composición de funciones, la paralelización de tareas con Streams paralelos y una mejor legibilidad en ciertas operaciones. En sistemas de alto rendimiento, los Streams pueden ofrecer un rendimiento competitivo o superior en operaciones de gran volumen con colecciones, especialmente si se aprovechan los Streams paralelos en CPUs multi-núcleo, aunque con la sobrecarga inicial de la creación del Stream y el boxing/unboxing en tipos primitivos. La clave es usarlos apropiadamente: los Streams son excelentes para procesamiento de datos, filtrado y mapeo; los Lambdas para simplificar la lógica de devolución de llamada. Para un rendimiento óptimo, se deben evitar las operaciones con estado, comprender el costo de las lambdas en línea frente a las referencias a métodos, y considerar el uso de bucles imperativos para tareas muy sensibles al rendimiento en colecciones pequeñas o cuando la sobrecarga de un Stream no se justifica. Optional reduce los errores de NullPointerException pero debe usarse para indicar la ausencia de valor, no como un contenedor de propósito general.

El Java Platform Module System (JPMS) y el fuerte encapsulamiento de los internos del JDK, que se endurecieron en Java 17, han redefinido la gestión de dependencias y la modularidad. ¿Qué desafíos arquitectónicos y estrategias de migración clave enfrentan los desarrolladores al adaptar aplicaciones monolíticas existentes o construir nuevas aplicaciones dentro de este paradigma modular? Considera específicamente el impacto en las librerías de terceros y el uso de la reflexión.

JPMS (Java 9+) y el fuerte encapsulamiento (Java 17 por defecto) buscan mejorar la seguridad, la mantenibilidad y el rendimiento. Los desafíos arquitectónicos incluyen la necesidad de definir explícitamente las dependencias de módulos (module-info.java) y exportar paquetes. Las aplicaciones monolíticas a menudo deben refactorizarse en módulos lógicos o ejecutarse como un módulo único no nombrado (unnamed module), lo que puede generar advertencias o errores si acceden a APIs internas del JDK. Para librerías de terceros, es crucial que sean compatibles con JPMS; de lo contrario, se pueden usar 'automatic modules' (el nombre del JAR se convierte en nombre del módulo). La reflexión se ve afectada porque el fuerte encapsulamiento restringe el acceso a APIs internas del JDK, incluso mediante reflexión, a menos que se use la opción '--add-opens' en tiempo de ejecución. Las estrategias de migración implican analizar las dependencias para la compatibilidad con JPMS, refactorizar el código para minimizar el uso de APIs internas y preparar el código para una modularización progresiva, además de asegurar que las herramientas de construcción y CI/CD soporten JPMS.

Java ha introducido nuevos recolectores de basura como ZGC y Shenandoah, y ha mejorado G1. Compara y contrasta los objetivos arquitectónicos y las características operativas de G1, ZGC y Shenandoah. ¿En qué escenarios de aplicaciones de alto rendimiento y baja latencia recomendarías uno sobre los otros, y cuáles son las consideraciones clave para su optimización?

G1 (Garbage-First) es el GC por defecto desde Java 9, diseñado para aplicaciones con heaps grandes, buscando equilibrar alto throughput con pausas predecibles (menos de 200ms). Divide el heap en regiones y recolecta las que tienen más basura primero. ZGC (Java 11+) y Shenandoah (Java 12+, con su propio JEP en Java 17) son recolectores concurrentes y pauseless (pausas típicamente por debajo de 1-10ms), escalables a heaps multi-terabyte. Su objetivo arquitectónico principal es eliminar las pausas de GC relacionadas con el tamaño del heap, realizando la mayor parte del trabajo de recolección concurrentemente con el programa de aplicación. ZGC utiliza 'colored pointers' para rastrear referencias, mientras que Shenandoah emplea 'load references' para la reubicación concurrente. Para aplicaciones con alto throughput donde las pausas ocasionales de unos cientos de milisegundos son aceptables, G1 es una excelente opción equilibrada. Para aplicaciones de muy baja latencia, donde cada milisegundo de pausa es crítico (ej. trading de alta frecuencia, bases de datos in-memory), ZGC o Shenandoah son preferibles, ya que pueden manejar heaps enormes con pausas casi constantes e insignificantes. La optimización para G1 implica ajustar el tamaño del heap y los parámetros de pausa máxima. Para ZGC y Shenandoah, la optimización se centra más en asegurar suficiente CPU para el trabajo concurrente del GC y elegir un tamaño de heap que evite la presión excesiva, ya que su modelo 'pauseless' reduce drásticamente la necesidad de ajustar los umbrales de pausa.

Java 14 introdujo los Records y Java 17 finalizó las Sealed Classes. ¿Cómo cambian estas características fundamentalmente el enfoque del modelado de datos y el diseño de dominio en las aplicaciones Java modernas? Discute sus beneficios en términos de reducción de boilerplate, inmutabilidad y aplicación de jerarquías de tipos, y proporciona un escenario donde simplifican significativamente una lógica de dominio compleja.

Records y Sealed Classes mejoran drásticamente el modelado de datos y el diseño de dominio. Los Records (clases de datos inmutables) reducen el boilerplate para las clases que solo contienen datos, generando automáticamente constructores, getters, equals(), hashCode() y toString(). Esto fomenta la inmutabilidad y la claridad del código, ideal para DTOs (Data Transfer Objects), valores de dominio y tuplas. Las Sealed Classes permiten a los desarrolladores declarar qué clases o interfaces pueden implementar o extender una interfaz o clase sellada, respectivamente. Esto proporciona un control exhaustivo sobre las jerarquías de tipos, lo que es útil para modelar dominios donde un tipo solo puede tener un conjunto finito y conocido de subtipos, como en los tipos algebraicos de datos. Los beneficios son la seguridad de tipo mejorada, el mantenimiento facilitado y la capacidad de realizar un 'pattern matching' exhaustivo en las sentencias switch (con JEPs adicionales), evitando errores en tiempo de ejecución. Un escenario simplificado sería el modelado de un 'Resultado' de una operación, que podría ser 'Éxito' o 'Fallo'. Con Sealed Classes, se puede definir una interfaz sealed interface Resultado permits Exito, Fallo {}, y luego record Exito(Object valor) implements Resultado {} y record Fallo(String mensaje) implements Resultado {}. Esto asegura que solo estos dos tipos puedan ser un 'Resultado', y un switch sobre Resultado puede verificar exhaustivamente ambos casos, lo que simplifica la lógica de manejo de errores y evita el boilerplate de crear múltiples clases de datos mutables.

Dada la rápida cadencia de lanzamiento de Java (cada 6 meses, con LTS cada dos años), ¿cuáles son las consideraciones arquitectónicas primarias al diseñar una nueva aplicación hoy para asegurar futuras actualizaciones fluidas a través de versiones LTS y no LTS? Discute el equilibrio entre la adopción de las últimas características del lenguaje y el mantenimiento de la compatibilidad, especialmente con dependencias de terceros y librerías internas.

La principal consideración arquitectónica es minimizar la 'fricción' en futuras actualizaciones. Esto implica diseñar con una clara separación de preocupaciones y una fuerte cohesión de módulos. Para la adopción de características: priorizar el uso de características maduras y estables de las versiones LTS. Las características de vista previa (preview features) o las incubadoras deben usarse con precaución en producción, ya que sus APIs pueden cambiar. Para dependencias de terceros, es crucial elegir librerías bien mantenidas que se actualicen rápidamente para soportar las nuevas versiones de Java y JPMS. Se debe mantener un ojo en los posibles abandonos de características o el fuerte encapsulamiento que podría romper el código o las librerías. Para las librerías internas, es vital que sigan buenas prácticas de diseño API y eviten depender de APIs internas del JDK. Utilizar herramientas como Maven o Gradle para gestionar dependencias de forma robusta, realizar pruebas de regresión exhaustivas y tener una estrategia de CI/CD que incluya la prueba con nuevas versiones de Java antes de la adopción en producción. La decisión de migrar a versiones no LTS debe basarse en el valor de las nuevas características para el negocio y la capacidad del equipo para gestionar las actualizaciones más frecuentes, equilibrando la 'agilidad de la versión' con la estabilidad operativa.
