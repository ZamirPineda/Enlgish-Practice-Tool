Explicación Profunda de JWT (JSON Web Tokens)

JWT (JSON Web Token) es un estándar abierto (RFC 7519) para la creación de tokens de acceso que permiten la transmisión segura de información entre partes como un objeto JSON compacto y auto-contenido. Es ampliamente utilizado para la autenticación y autorización en arquitecturas distribuidas, especialmente APIs RESTful y microservicios.

Conceptos Fundamentales:

La idea principal detrás de JWT es permitir que un servidor (o proveedor de identidad) genere un token que contenga información sobre el usuario (claims) después de una autenticación exitosa. Este token es firmado criptográficamente por el servidor, lo que garantiza su integridad y autenticidad. El cliente almacena este token y lo envía en cada solicitud subsecuente al servidor. El servidor puede verificar la firma del token para asegurarse de que no ha sido alterado y para confiar en la información contenida en él, sin necesidad de consultar una base de datos de sesiones o estados. Esto conduce a una autenticación sin estado (stateless).

Arquitectura Interna:

Un JWT se compone de tres partes separadas por puntos (.):

1. Header (Cabecera):

  • * Es un objeto JSON que describe el tipo de token (JWT) y el algoritmo de firma utilizado.
  • * Ejemplo: {"alg": "HS256", "typ": "JWT"}
  • * alg: Especifica el algoritmo de firma que se utiliza para firmar el token (por ejemplo, HMAC SHA256 o RSA).
  • * typ: Especifica que el tipo de token es "JWT".

2. Payload (Carga Útil o Claims):

  • * Es un objeto JSON que contiene las "claims" (declaraciones) o afirmaciones sobre una entidad (normalmente el usuario) y datos adicionales. Hay tres tipos de claims:
  • * Registered Claims: Un conjunto de claims predefinidas y recomendadas, pero no obligatorias. Ofrecen un buen punto de partida para un conjunto de claims útiles e interoperables. Ejemplos: iss (issuer - emisor), sub (subject - sujeto), aud (audience - audiencia), exp (expiration time - tiempo de expiración), nbf (not before - no antes de), iat (issued at - emitido en), jti (JWT ID).
  • * Public Claims: Pueden ser definidas por los usuarios de JWT, pero para evitar colisiones, deben registrarse en el IANA JSON Web Token Registry o definirse como un URI que contenga un espacio de nombres resistente a colisiones.
  • * Private Claims: Son claims personalizadas creadas para compartir información entre las partes acordadas. No tienen restricciones de nombre y su uso es a discreción de las partes.

3. Signature (Firma):

  • * Se crea tomando la cabecera codificada en Base64url, la carga útil codificada en Base64url, un secreto (o clave privada) y el algoritmo especificado en la cabecera.
  • * HMACSHA256(base64UrlEncode(header) + "." + base64UrlEncode(payload), secret)
  • * La firma se utiliza para verificar que el token no ha sido alterado por un tercero y, en el caso de tokens firmados con clave privada/pública, para verificar que el emisor del JWT es quien dice ser.

Flujo de funcionamiento:

1. El cliente envía sus credenciales (nombre de usuario/contraseña) a un servidor de autenticación.

2. El servidor verifica las credenciales y, si son válidas, crea un JWT.

3. El servidor firma el JWT con un secreto (o su clave privada) y lo envía de vuelta al cliente.

4. El cliente almacena el JWT (ej. en localStorage, sessionStorage o cookies HTTP-Only).

5. En cada solicitud subsecuente a recursos protegidos, el cliente incluye el JWT, típicamente en el encabezado Authorization como Bearer .

6. El servidor de recursos intercepta la solicitud, verifica la firma del JWT (usando el mismo secreto o la clave pública correspondiente).

7. Si la firma es válida y el token no ha expirado, el servidor confía en los claims del payload y autoriza la solicitud. Si no, deniega el acceso.

Modelo de Datos/Comunicación:

  • Modelo de Datos: El JWT encapsula datos (claims) en un objeto JSON, que luego se codifica y se firma. Los datos son auto-contenidos, lo que significa que toda la información necesaria para la autenticación y autorización básica está dentro del token mismo, eliminando la necesidad de consultas adicionales a una base de datos de sesiones para cada solicitud.
  • Comunicación: El JWT se transmite típicamente sobre HTTP(S). El método más común es incluirlo en el encabezado Authorization como un token Bearer. Esto permite que los clientes (navegadores, aplicaciones móviles, etc.) envíen el token fácilmente junto con sus solicitudes a la API. Al ser URL-safe, también puede ser enviado en parámetros de consulta (aunque no es lo ideal por razones de seguridad y logs).

Ventajas Clave y Desventajas:

#### Ventajas Clave:

  • Statelessness (Sin estado): El servidor no necesita almacenar el estado de la sesión, lo que simplifica la arquitectura, mejora la escalabilidad horizontal (distribuir la carga entre múltiples servidores) y facilita la implementación en arquitecturas de microservicios.
  • Auto-contenido: Toda la información relevante sobre el usuario y sus permisos está dentro del token, reduciendo la necesidad de consultas a la base de datos para cada solicitud.
  • Compacto: Debido a su pequeño tamaño, los JWT pueden ser enviados rápidamente a través de la red, incluso dentro de URLs o parámetros de POST.
  • Movilidad y soporte multi-plataforma: Es un estándar que puede ser utilizado por diferentes clientes (web, móvil, desktop) para interactuar con APIs RESTful.
  • Desacoplamiento: El proveedor de identidad puede ser independiente del servidor de recursos, lo que es ideal para Single Sign-On (SSO) y federación de identidades.
  • Seguridad: La firma criptográfica garantiza la integridad del token (no ha sido alterado) y la autenticidad (proviene de una fuente confiable).

#### Desventajas:

  • Sin revocación fácil: Una vez que un JWT ha sido emitido y firmado, es válido hasta su expiración. No hay un mecanismo estándar incorporado para revocar un token antes de tiempo. Esto requiere soluciones alternativas como listas negras (blacklists) o períodos de expiración muy cortos.
  • Tamaño del token: Si se incluyen demasiadas claims en el payload, el token puede volverse grande, lo que aumenta el overhead en cada solicitud.
  • Seguridad del secreto: Si el secreto utilizado para firmar los tokens es comprometido, un atacante podría forjar tokens válidos, comprometiendo todo el sistema.
  • Almacenamiento en el cliente: Si el JWT se almacena en el localStorage del navegador, puede ser vulnerable a ataques XSS (Cross-Site Scripting). Si se almacena en cookies, puede ser vulnerable a ataques CSRF (Cross-Site Request Forgery) si no se utilizan las mitigaciones adecuadas (HttpOnly, SameSite=Lax/Strict).
  • No cifrado por defecto: Por defecto, el payload de un JWT solo está codificado en Base64url, no cifrado. Esto significa que cualquier información sensible en el payload es legible por cualquiera que intercepte el token. Para la confidencialidad, se necesita JWE (JSON Web Encryption).

Preguntas de Entrevista sobre JWT (JSON Web Tokens)

Pregunta 1: Explica la estructura de un JWT y el propósito de cada una de sus tres partes. ¿Cómo se verifica un JWT en el servidor?

Respuesta detallada:

Un JWT se compone de tres partes separadas por puntos (.) al ser serializado: Header, Payload y Signature.

1. Header (Cabecera): Es un objeto JSON que contiene metadatos sobre el token. Mínimamente, especifica el algoritmo de firma (alg) y el tipo de token (typ, que casi siempre es "JWT"). Se codifica en Base64url. Su propósito es informar al receptor cómo debe interpretar y verificar el token.

2. Payload (Carga Útil/Claims): Es un objeto JSON que contiene las "claims" o declaraciones. Estas claims son pares clave-valor que representan atributos sobre la entidad (generalmente el usuario autenticado) y otros datos. Pueden ser Registered Claims (estándar como iss, exp, sub), Public Claims (registradas públicamente) o Private Claims (personalizadas para la aplicación). También se codifica en Base64url. Su propósito es transportar la información de forma auto-contenida.

3. Signature (Firma): Se genera concatenando el Header y el Payload (ambos codificados en Base64url y separados por un punto), y luego aplicando el algoritmo de firma especificado en el Header, utilizando un secreto (para algoritmos simétricos como HS256) o una clave privada (para algoritmos asimétricos como RS256). Su propósito fundamental es garantizar la integridad del token (que no ha sido alterado desde su emisión) y su autenticidad (que fue emitido por el servidor legítimo).

Verificación en el servidor:

Cuando un servidor recibe un JWT, realiza los siguientes pasos de verificación:

1. Decodificar Header y Payload: Las partes del Header y el Payload se decodifican de Base64url para leer sus contenidos.

2. Verificar Algoritmo y Tipo: Se verifica que el typ sea "JWT" y que el alg sea uno de los algoritmos esperados y seguros. Es crucial evitar la vulnerabilidad del algoritmo "None".

3. Generar Firma esperada: El servidor toma el Header y el Payload decodificados, los vuelve a codificar en Base64url, los concatena y utiliza el mismo secreto (o la clave pública correspondiente a la clave privada del emisor) y el algoritmo especificado en el Header para generar una firma esperada.

4. Comparar Firmas: La firma generada por el servidor se compara con la firma original presente en el JWT. Si ambas coinciden, se confirma la integridad y autenticidad del token. Si no, el token es inválido.

5. Validar Claims: Finalmente, el servidor valida las claims dentro del Payload. Esto incluye verificar el tiempo de expiración (exp), el tiempo "no antes de" (nbf), el emisor (iss) y la audiencia (aud) para asegurarse de que el token es actualmente válido y destinado a este servidor.

Pregunta 2: ¿Cuál es el principal desafío de la revocación de JWTs, y qué estrategias comunes se utilizan para mitigarlo en sistemas de producción?

Respuesta detallada:

El principal desafío de la revocación de JWTs radica en su naturaleza sin estado (stateless) y auto-contenido. Una vez que un JWT ha sido emitido y firmado, es intrínsecamente válido hasta que expira, ya que el servidor no mantiene ningún estado de sesión asociado al token. Esto significa que si un token es comprometido (robado), o si un usuario necesita ser deshabilitado de inmediato (por ejemplo, cambio de contraseña, cierre de sesión forzado), no hay un mecanismo directo para invalidarlo antes de su tiempo de vida útil (exp).

Estrategias comunes para mitigar este desafío:

1. Períodos de expiración cortos (Short Expiration Times): Esta es la mitigación más fundamental. Al establecer un exp muy corto (ej. 5-15 minutos), el impacto de un token comprometido se reduce, ya que pronto dejará de ser válido. Sin embargo, esto requiere que el cliente solicite nuevos tokens de acceso con frecuencia, lo cual puede degradar la experiencia de usuario si no se combina con tokens de refresco.

2. Tokens de Refresco (Refresh Tokens): Para mejorar la experiencia de usuario con exp cortos, se introducen los tokens de refresco. Un token de acceso de corta duración se emite junto con un token de refresco de larga duración.

  • * El token de acceso se usa para acceder a recursos protegidos.
  • * Cuando el token de acceso expira, el cliente usa el token de refresco (enviado a un endpoint de refresco dedicado) para obtener un nuevo par de token de acceso/refresco.
  • Los tokens de refresco son stateful* y se almacenan en el servidor (ej., en una base de datos o caché). Esto permite al servidor revocar un token de refresco en cualquier momento, invalidando así la capacidad del cliente para obtener nuevos tokens de acceso. Si un usuario cierra sesión o cambia su contraseña, se revoca el token de refresco asociado.

3. Listas Negras (Blacklists/Blocklists): El servidor puede mantener una lista de JWTs que han sido revocados prematuramente. Cada vez que se recibe un JWT, el servidor lo verifica contra esta lista negra. Si el token está en la lista, se rechaza.

  • * Pros: Permite la revocación instantánea.
  • * Contras: Introduce estado en el servidor (aunque sea solo para la lista negra), lo que puede afectar la escalabilidad y requiere una base de datos o caché distribuida y rápida (ej., Redis) para un buen rendimiento. Puede haber problemas de latencia entre múltiples instancias de servicio.

4. Verificación en Bases de Datos (Database Lookups): En algunos casos, se puede incluir una claim en el JWT (ej., jti - JWT ID) que se asocia a un registro en la base de datos del usuario. Antes de autorizar, el servidor verifica si el jti todavía es válido o si el usuario asociado sigue activo. Esto también introduce estado y aumenta la latencia, ya que cada solicitud requiere una consulta a la base de datos.

5. Cambio de Secreto de Firma: Si un atacante roba el secreto de firma, se pueden forjar tokens. Cambiar el secreto de firma invalidará instantáneamente todos los JWTs emitidos previamente (excepto si se maneja una rotación de claves sofisticada), forzando a todos los usuarios a volver a autenticarse. Esta es una medida drástica para escenarios de compromiso crítico.

La combinación más común y robusta es el uso de períodos de expiración cortos para los tokens de acceso y tokens de refresco gestionados de forma stateful para la revocación.

Pregunta 3: ¿Cómo facilita JWT la autenticación sin estado (stateless) y por qué es esto beneficioso para arquitecturas de microservicios?

Respuesta detallada:

JWT facilita la autenticación sin estado porque toda la información necesaria para verificar la autenticidad del usuario y sus permisos está contenida dentro del token mismo. A diferencia de las sesiones tradicionales basadas en cookies, donde el servidor almacena un identificador de sesión y debe consultarlo en su propia memoria o base de datos para cada solicitud, con JWT:

  • El servidor no necesita almacenar el estado de la sesión: Una vez que el servidor de autenticación emite el JWT, olvida la sesión. El cliente es responsable de almacenar y enviar el token en cada solicitud.
  • Auto-verificación: Cualquier servidor que posea el secreto de firma (o la clave pública) puede verificar de forma independiente la validez y la integridad del token, así como confiar en los claims contenidos en él, sin necesidad de comunicarse con el servidor de autenticación o una base de datos de sesiones compartida.

Beneficios para arquitecturas de microservicios:

1. Escalabilidad horizontal: Al no tener estado de sesión en el servidor, cualquier instancia de un microservicio puede procesar cualquier solicitud. Esto permite escalar el número de instancias de servicio de forma elástica, simplemente añadiendo o quitando servidores sin preocuparse por la replicación o sincronización de estados de sesión. Los balanceadores de carga pueden distribuir solicitudes entre microservicios sin "stickiness" (adherencia de sesión).

2. Desacoplamiento e independencia: Cada microservicio puede verificar el JWT de forma independiente. No necesitan compartir una base de datos de sesiones centralizada ni comunicarse con un servicio de sesión específico. Esto reduce las dependencias entre servicios y permite que los equipos desarrollen y desplieguen microservicios de forma autónoma.

3. Tolerancia a fallos: Si un microservicio falla, no se pierde ninguna información de sesión crítica en ese microservicio, ya que el estado reside en el cliente. Otros microservicios pueden seguir operando sin interrupciones.

4. Menos sobrecarga de red: El tráfico de red se reduce al eliminar la necesidad de que los microservicios consulten repetidamente un almacén de sesiones centralizado.

5. Single Sign-On (SSO) simplificado: En un entorno de microservicios, un usuario puede autenticarse una vez con un servicio de identidad (que emite el JWT) y luego usar ese mismo JWT para acceder a múltiples microservicios sin volver a autenticarse en cada uno.

En resumen, la naturaleza sin estado de JWT es fundamental para la agilidad, escalabilidad y resiliencia inherentes a las arquitecturas de microservicios, permitiendo una gestión de la autenticación y autorización distribuida y eficiente.

Pregunta 4: Discute las implicaciones de seguridad de almacenar JWTs en localStorage versus HttpOnly cookies. ¿Cuál es generalmente preferido para qué casos de uso?

Respuesta detallada:

La elección de dónde almacenar un JWT en el cliente (navegador) tiene importantes implicaciones de seguridad:

1. Almacenamiento en localStorage (o sessionStorage):

  • Ventajas:
  • * Accesible vía JavaScript: Permite a la aplicación JavaScript del frontend leer y adjuntar el token fácilmente a las cabeceras Authorization de las peticiones AJAX/Fetch.
  • * No se envía automáticamente: El token no se adjunta automáticamente a cada solicitud por el navegador, lo que da un control explícito sobre cuándo y a qué dominios se envía.
  • Desventajas (riesgos de seguridad):
  • * Vulnerable a XSS (Cross-Site Scripting): Si un atacante logra inyectar código JavaScript malicioso en tu sitio web (a través de una vulnerabilidad XSS), ese script puede acceder al localStorage y robar el JWT. Una vez robado, el atacante puede usarlo para suplantar al usuario. Esta es la principal preocupación.
  • * No hay protección CSRF nativa: Aunque el token no se envía automáticamente, si un atacante puede ejecutar JavaScript en tu origen, puede usar el token para hacer peticiones en tu nombre.

2. Almacenamiento en HttpOnly Cookies:

  • Ventajas:
  • * Protección contra XSS: Al marcar una cookie como HttpOnly, el JavaScript del navegador no puede acceder a ella. Esto significa que incluso si hay una vulnerabilidad XSS, el atacante no puede robar directamente el JWT de la cookie.
  • * Envío automático: El navegador adjunta automáticamente las cookies a cada solicitud del dominio al que pertenecen, lo que simplifica la implementación en el frontend (no es necesario añadir el token manualmente a cada cabecera).
  • *Protección CSRF (con SameSite): Con el atributo SameSite (Lax o Strict), las cookies pueden protegerse eficazmente contra ataques CSRF, ya que el navegador no las enviará en solicitudes de origen cruzado.
  • Desventajas (riesgos de seguridad):
  • *Vulnerable a CSRF (sin SameSite o con SameSite=None sin precauciones): Si no se usa SameSite=Lax o Strict (o un token CSRF adicional), un atacante puede engañar al navegador para que envíe la cookie a tu servidor en una solicitud maliciosa desde otro sitio web.
  • * No accesible vía JavaScript: Al ser HttpOnly, la aplicación frontend no puede leer el token directamente, lo que puede dificultar ciertas lógicas de interfaz de usuario basadas en el token.
  • * Problemas de dominios cruzados: Las cookies están ligadas a un dominio. Si tu API está en un subdominio diferente o un dominio completamente distinto, configurar las cookies correctamente puede ser más complejo.

Preferencia General y Casos de Uso:

Generalmente, las HttpOnly cookies con Secure y SameSite=Lax o Strict son consideradas la opción más segura para almacenar tokens de acceso JWT en aplicaciones web tradicionales (monolitos o SPAs que interactúan con un backend del mismo origen). Esto se debe a que la protección contra XSS (por HttpOnly) es crucial, ya que un XSS puede llevar a comprometer completamente la cuenta del usuario. La mitigación de CSRF con SameSite es también muy efectiva.

localStorage es a menudo utilizado por su facilidad de uso y flexibilidad, especialmente en arquitecturas donde el frontend y el backend están en dominios completamente separados (ej. app.com y api.com), o en aplicaciones móviles/desktop donde los riesgos de XSS son diferentes. Sin embargo, su uso requiere una higiene de seguridad extremadamente rigurosa para prevenir XSS. Si se elige localStorage, es imperativo implementar una Content Security Policy (CSP) estricta y escanear el código regularmente para vulnerabilidades XSS.

Conclusión: Para la mayoría de las aplicaciones web, especialmente las que comparten el mismo dominio entre frontend y backend, las HttpOnly cookies son preferibles por sus protecciones inherentes contra XSS y CSRF. Si localStorage es la única opción viable, la prevención de XSS debe ser la máxima prioridad de seguridad.

Pregunta 5: Explica qué son los tokens de refresco (Refresh Tokens) y cómo se utilizan en conjunto con los tokens de acceso para mejorar la seguridad y la experiencia del usuario.

Respuesta detallada:

Los tokens de refresco son credenciales de larga duración que se utilizan para obtener nuevos tokens de acceso de corta duración sin requerir que el usuario se reautentique. Trabajan en conjunto con los tokens de acceso para balancear la seguridad y la usabilidad.

Funcionamiento:

1. Autenticación Inicial: El usuario se autentica con sus credenciales (nombre de usuario/contraseña) ante el servidor de autenticación.

2. Emisión de Tokens: Si la autenticación es exitosa, el servidor emite dos tokens:

  • * Un Token de Acceso (Access Token): Un JWT de corta duración (ej. 5-15 minutos) que se utiliza para acceder a los recursos protegidos de la API. Este es el token que el cliente adjunta a cada solicitud a los microservicios o recursos.
  • * Un Token de Refresco (Refresh Token): Un token de larga duración (ej. días, semanas o incluso meses) que es opaco (no es un JWT) o un JWT sin claims sensibles y con una firma diferente. Se utiliza para solicitar nuevos tokens de acceso.

3. Almacenamiento y Uso por el Cliente:

  • * El cliente almacena el token de acceso (ej. en localStorage o sessionStorage) y lo envía con cada solicitud a la API.
  • * El cliente almacena el token de refresco de forma más segura (ej. en una HttpOnly cookie, que es inaccesible por JavaScript, o en un almacenamiento seguro en el caso de aplicaciones móviles).

4. Expiración del Token de Acceso: Cuando el token de acceso expira (lo que ocurre rápidamente), las solicitudes a la API fallan con un error de "Unauthorized".

5. Obtención de un Nuevo Token de Acceso: El cliente envía el token de refresco al endpoint de "refresco" del servidor de autenticación.

6. Verificación y Nueva Emisión: El servidor verifica el token de refresco (generalmente consultando una base de datos para asegurarse de que no ha sido revocado). Si es válido, emite un nuevo par de token de acceso y (opcionalmente) un nuevo token de refresco.

7. Ciclo Continuo: El cliente reemplaza el token de acceso expirado con el nuevo y continúa accediendo a los recursos sin interrupción para el usuario.

Mejora de Seguridad y Experiencia de Usuario:

  • Mejora de Seguridad:
  • * Reducción del riesgo de tokens comprometidos: Los tokens de acceso tienen una vida útil muy corta. Si un token de acceso es interceptado, su ventana de utilidad para un atacante es limitada.
  • Revocación efectiva: Los tokens de refresco son stateful* (el servidor los almacena y rastrea). Si el usuario cambia su contraseña, cierra sesión o hay actividad sospechosa, el servidor puede revocar el token de refresco asociado, impidiendo que se emitan nuevos tokens de acceso y forzando al usuario a reautenticarse. Esto resuelve el problema de revocación instantánea de JWTs.
  • * Almacenamiento seguro: Al almacenar el token de refresco en una HttpOnly cookie (o almacenamiento seguro fuera del alcance de JavaScript), se mitiga el riesgo de robo por ataques XSS.
  • Mejora de la Experiencia del Usuario:
  • * Sesiones de larga duración: Los usuarios pueden permanecer autenticados durante períodos prolongados sin tener que introducir sus credenciales repetidamente, ya que el token de refresco gestiona la renovación silenciosa del token de acceso.
  • * Transparencia: El proceso de renovación de tokens es transparente para el usuario final, que simplemente experimenta una sesión fluida.

En resumen, los tokens de refresco son una pieza fundamental en la implementación de la autenticación basada en JWT, permitiendo una solución robusta que combina la eficiencia sin estado de los JWT de acceso con la capacidad de revocación y una mejor seguridad y usabilidad.

Pregunta 6: Explica la diferencia entre JWS (JSON Web Signature) y JWE (JSON Web Encryption). ¿Cuándo se usaría uno sobre el otro?

Respuesta detallada:

JWS y JWE son dos estándares complementarios dentro de la familia JOSE (JSON Object Signing and Encryption) que abordan diferentes aspectos de la seguridad de la información.

1. JWS (JSON Web Signature):

  • * Propósito: Proporciona un mecanismo para garantizar la integridad y la autenticidad de los datos. Esto significa que puedes verificar que los datos no han sido alterados en tránsito y que provienen de una fuente de confianza.
  • * Funcionamiento: Un JWS consiste en una cabecera protegida, una carga útil (payload) y una firma. La carga útil no está cifrada, solo codificada en Base64url, lo que la hace legible por cualquiera que intercepte el JWS. La firma se genera a partir de la cabecera y el payload usando un algoritmo criptográfico (ej. HMAC SHA256 o RSA).
  • * Formato: Base64url(JWS Header) . Base64url(JWS Payload) . Base64url(JWS Signature)
  • * Cuándo usarlo: Cuando la confidencialidad no es una preocupación (es decir, la información del payload no es sensible y puede ser visible para terceros), pero la integridad y la autenticidad son críticas. Este es el caso de la mayoría de los tokens JWT estándar, donde el payload contiene claims no sensibles (ID de usuario, roles, tiempo de expiración) que no requieren cifrado.

2. JWE (JSON Web Encryption):

  • * Propósito: Proporciona un mecanismo para garantizar la confidencialidad de los datos, es decir, que los datos solo pueden ser leídos por el destinatario previsto. También incluye mecanismos de integridad.
  • * Funcionamiento: Un JWE cifra la carga útil (payload) de los datos. Utiliza una cabecera protegida (que describe los algoritmos de cifrado y empaquetamiento de claves), la clave de cifrado (que también está cifrada para el destinatario), el vector de inicialización, la carga útil cifrada y una etiqueta de autenticación (para verificar la integridad del cifrado).
  • * Formato: Base64url(JWE Header) . Base64url(Encrypted Key) . Base64url(Initialization Vector) . Base64url(Ciphertext) . Base64url(Authentication Tag)
  • * Cuándo usarlo: Cuando la confidencialidad es una preocupación principal, es decir, la información en la carga útil es sensible y no debe ser legible por partes no autorizadas. Por ejemplo, si necesitas incluir información de identificación personal (PII), datos de salud, información financiera o cualquier dato que deba mantenerse en secreto en el token.

Relación con JWT:

Un JWT puede ser un JWS o un JWE.

  • Si un JWT necesita solo integridad y autenticidad, se implementa como un JWS. Este es el uso más común y el que generalmente se entiende cuando se habla de "JWT".
  • Si un JWT necesita confidencialidad (además de integridad y autenticidad), se implementa como un JWE. A menudo, se podría tener un JWT (JWS) anidado dentro de un JWE para primero firmar y luego cifrar las claims.

En resumen, elige JWS para datos que pueden ser públicos pero deben ser de confianza, y JWE para datos que deben ser secretos.

Pregunta 7: Describe la vulnerabilidad del algoritmo "None" en JWT y cómo se puede mitigar.

Respuesta detallada:

La vulnerabilidad del algoritmo "None" es un riesgo de seguridad crítico en JWTs que surge cuando la implementación del verificador de JWT no valida correctamente el algoritmo de firma especificado en la cabecera del token.

La Vulnerabilidad:

El estándar JWT permite explícitamente el uso de alg: "none" en la cabecera para indicar que el token no está firmado. Esto tiene un propósito legítimo en ciertos escenarios (ej. tokens que se envían por un canal seguro y donde la firma es redundante o no deseada).

El problema ocurre cuando un servidor que espera un token firmado (por ejemplo, con HS256 o RS256) no fuerza explícitamente la verificación de que el algoritmo no sea "none". Un atacante puede tomar un token válido, cambiar el alg en su cabecera a "none", eliminar la parte de la firma, y luego enviárselo al servidor. Si el servidor no verifica que el algoritmo de firma sea el esperado y permitido, simplemente decodificará el payload y aceptará sus claims como válidas, asumiendo que el token es auténtico. Esto permite al atacante forjar tokens con claims arbitrarias y suplantar usuarios.

Ejemplo de ataque:

1. Servidor emite JWT_VALID = { "alg": "HS256", "typ": "JWT" } . { "sub": "usuario_real", "role": "user" } . [firma_válida]

2. Atacante captura JWT_VALID.

3. Atacante modifica el JWT a JWT_FORGED = { "alg": "none", "typ": "JWT" } . { "sub": "admin", "role": "admin" } . (sin firma).

4. Si el servidor tiene la vulnerabilidad, aceptará JWT_FORGED como válido, concediendo privilegios de administrador al atacante.

Mitigación:

La mitigación de esta vulnerabilidad es fundamental y relativamente sencilla:

1. Validación Explícita del Algoritmo: El servidor siempre debe verificar el algoritmo de firma (alg) especificado en la cabecera del JWT contra una lista blanca de algoritmos esperados y permitidos (ej., HS256, RS256).

  • *Nunca permitir alg: "none" si se espera un token firmado.
  • * Si se usa una biblioteca JWT, asegúrate de configurarla para que rechace el algoritmo "none" por defecto o para que solo acepte algoritmos específicos. La mayoría de las bibliotecas JWT modernas lo hacen por defecto o proporcionan opciones para configurar los algoritmos permitidos.

2. Configuración de Claves: Al verificar un token, asegúrate de que el verificador esté configurado para usar la clave de firma esperada y que falle si no puede verificar la firma con esa clave y el algoritmo especificado.

3. Auditoría de Código: Revisar el código que maneja la verificación de JWTs para asegurar que no hay rutas de ejecución que permitan el procesamiento de tokens sin firma o con algoritmos inesperados.

La clave es que la confianza en un JWT no debe basarse solo en la presencia de un token, sino en la correcta verificación de su firma utilizando el algoritmo esperado y una clave secreta/pública válida.

Tópicos Avanzados y Errores Comunes

1. Error Común: Sobrecargar el Payload del JWT

Descripción: Un error frecuente es incluir demasiada información en el payload del JWT. A menudo, los desarrolladores se sienten tentados a añadir una gran cantidad de datos sobre el usuario (preferencias, detalles de perfil extensos, listas de permisos granulares) para evitar futuras llamadas a la base de datos.

Consecuencias:

  • Aumento del tamaño del token: Un JWT grande aumenta el tráfico de red en cada solicitud y puede impactar negativamente el rendimiento.
  • Exposición de datos sensibles: Dado que el payload solo está codificado en Base64url (no cifrado por defecto), todos los datos en él son legibles. Incluir información personal identificable (PII) o datos sensibles es un riesgo de seguridad si el token es interceptado.
  • Problemas de escalabilidad: Si los datos del usuario cambian frecuentemente, el token podría quedar desactualizado rápidamente, forzando renovaciones frecuentes o incoherencias.

Solución/Práctica Avanzada:

  • Principio de "Menos es Más": El payload del JWT debe contener solo la información esencial y de bajo riesgo necesaria para identificar al usuario y determinar su autorización básica. Ejemplos: sub (ID de usuario), roles (alto nivel), exp.
  • Claims para datos dinámicos: Para datos más detallados o que cambian con frecuencia (ej. últimas compras, preferencias detalladas), es mejor guardar una referencia (ej. un ID de usuario) en el token y hacer una llamada a una API protegida por ese token para obtener esos datos.
  • Utilizar JWE para confidencialidad: Si realmente necesitas incluir datos sensibles en el token, entonces utiliza JWE (JSON Web Encryption) para cifrar el payload, no solo codificarlo.

2. Tópico Avanzado: Gestión de Claves con JWK (JSON Web Key) y JWKS (JSON Web Key Set)

Descripción: En entornos distribuidos, como microservicios o federaciones de identidad (ej., OpenID Connect), un servicio (el "emisor" o iss) firma JWTs y otros servicios (los "consumidores" o aud) necesitan verificar esas firmas. Compartir el "secreto" (HS256) o la "clave pública" (RS256, ES256) de manera segura y eficiente entre múltiples servicios puede ser un desafío. Aquí es donde entran JWK y JWKS.

  • JWK (JSON Web Key): Es una estructura de datos JSON que representa una clave criptográfica. Puede representar una clave pública o privada, y contiene metadatos como el tipo de clave (kty), el algoritmo (alg), el uso de la clave (use), y el identificador de la clave (kid).
  • JWKS (JSON Web Key Set): Es un objeto JSON que contiene un conjunto de JWKs.

Uso en la práctica:

1. Un servicio de autenticación (Identity Provider) que emite JWTs publica sus claves públicas de firma en un endpoint accesible públicamente (generalmente /.well-known/jwks.json).

2. Los servicios de recursos (Resource Servers) que necesitan verificar los JWTs obtienen las claves públicas del emisor consultando este endpoint JWKS.

3. Cuando un servicio de recursos recibe un JWT, lee el kid (Key ID) de la cabecera del JWT, lo busca en el JWKS que ha obtenido, y utiliza la clave pública correspondiente para verificar la firma del token.

Ventajas:

  • Descubrimiento automático de claves: Facilita la distribución y rotación de claves públicas sin necesidad de reconfigurar manualmente cada servicio consumidor.
  • Flexibilidad de algoritmos: Un JWKS puede contener claves para diferentes algoritmos, permitiendo al emisor cambiar de algoritmo si es necesario.
  • Robustez en sistemas distribuidos: Es un componente clave en la interoperabilidad de OpenID Connect y otras federaciones de identidad, permitiendo que múltiples partes confíen en los tokens emitidos por un solo emisor.

3. Error Común: No validar aud (Audience) y iss (Issuer)

Descripción: A menudo, los desarrolladores se centran únicamente en la verificación de la firma y el tiempo de expiración (exp) del JWT. Sin embargo, no validar las claims aud (audiencia) e iss (emisor) puede conducir a vulnerabilidades.

Consecuencias:

  • aud (Audience): Si el servidor de recursos no valida que el aud del token incluya su propia identidad, un JWT destinado a una aplicación completamente diferente podría ser aceptado. Esto se conoce como un ataque de "reproducción de token" o "token para una audiencia equivocada", donde un token válido para un servicio A es utilizado en el servicio B.
  • iss (Issuer): Si no se valida el iss, el servidor de recursos podría aceptar tokens de cualquier emisor, no solo del proveedor de identidad de confianza. Un atacante podría configurar su propio servidor JWT, firmar tokens con claims falsas, y si el recurso no verifica el iss, los aceptaría como válidos.

Solución/Práctica Avanzada:

  • Validación Estricta: Implementa una validación estricta para aud e iss.
  • * Para aud: El servidor de recursos debe verificar que el valor de la claim aud en el JWT contenga su propia URL o un identificador único que le ha sido asignado.
  • * Para iss: El servidor de recursos debe verificar que el valor de la claim iss coincida exactamente con el URL o identificador del proveedor de identidad de confianza que está configurado para emitir los tokens.
  • Bibliotecas JWT: La mayoría de las bibliotecas JWT de calidad ofrecen opciones de configuración para validar aud, iss, y otras claims registradas automáticamente durante el proceso de verificación. Utiliza estas características.

Al prestar atención a estos errores comunes y adoptar prácticas avanzadas, se puede construir una implementación JWT más robusta y segura.
