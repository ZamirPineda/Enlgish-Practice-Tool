Explicación Profunda de WAF (Web Application Firewall)

El Web Application Firewall (WAF) es una solución de seguridad que protege las aplicaciones web de ataques maliciosos interceptando, inspeccionando y filtrando el tráfico HTTP/S entre la aplicación web y los clientes que intentan acceder a ella. A diferencia de los firewalls de red tradicionales que operan en las capas de red y transporte (Capas 3 y 4 del modelo OSI), un WAF opera en la capa de aplicación (Capa 7), lo que le permite entender y analizar el contenido de las solicitudes y respuestas HTTP/S.

Conceptos Fundamentales

La idea principal detrás de un WAF es proporcionar una capa de seguridad específica para las aplicaciones web, mitigando ataques que los firewalls de red convencionales no pueden detectar. Estos ataques incluyen inyecciones SQL, Cross-Site Scripting (XSS), inclusión de archivos, ataques de día cero, manipulación de sesiones, y otras vulnerabilidades listadas en el OWASP Top 10. Actúa como un proxy inverso, examinando cada solicitud antes de que llegue a la aplicación web y cada respuesta antes de que llegue al cliente, basándose en un conjunto de reglas de seguridad predefinidas o aprendidas.

Arquitectura Interna

La arquitectura de un WAF típicamente involucra varios componentes clave y sigue un flujo de procesamiento de tráfico bien definido:

1. Punto de Intercepción: El WAF se despliega entre el cliente y la aplicación web. Puede ser un dispositivo de hardware, una instancia de software, o un servicio basado en la nube. Generalmente opera como un proxy inverso.

2. Terminación SSL/TLS: Para inspeccionar el tráfico cifrado (HTTPS), el WAF debe terminar la conexión SSL/TLS del cliente. Esto implica descifrar el tráfico, inspeccionarlo, y luego re-cifrarlo antes de enviarlo a la aplicación web (o reenviarlo sin cifrar si la comunicación interna es HTTP). Esto es crucial para la "inspección profunda de paquetes" (Deep Packet Inspection - DPI).

3. Motor de Reglas y Políticas: Este es el núcleo del WAF. Contiene un conjunto de reglas (firmas) que definen patrones de ataques conocidos y un motor lógico para evaluar el tráfico contra estas reglas. Las reglas pueden ser:

  • * Basadas en Firmas (Lista Negra): Identifican patrones de ataque específicos, como cadenas de inyección SQL o scripts XSS conocidos.
  • * Basadas en Anomalías (Detección de Anomalías): Construyen un perfil de comportamiento "normal" de la aplicación y marcan cualquier desviación como una anomalía potencial.
  • Basadas en Políticas Positivas (Lista Blanca): Definen qué tipos de solicitudes son permitidas* (ej. solo ciertos tipos de datos en ciertos campos, URLs específicas, métodos HTTP permitidos). Esto es más seguro pero más complejo de configurar.

4. Base de Datos de Firmas: Almacena los patrones de ataque actualizados regularmente.

5. Módulos de Seguridad Específicos: Muchos WAFs incluyen módulos para:

  • * Protección de Bots: Identifica y bloquea bots maliciosos.
  • * Gestión de Sesiones: Monitorea y protege contra el secuestro de sesiones.
  • * Rate Limiting: Previene ataques de fuerza bruta y denegación de servicio (DoS) limitando el número de solicitudes por usuario o IP.
  • * Virtual Patching: Permite aplicar parches de seguridad "virtuales" a vulnerabilidades conocidas en la aplicación subyacente sin modificar el código fuente.

6. Sistema de Logging y Reportes: Registra todas las solicitudes, las decisiones del WAF (permitir/bloquear) y los detalles de los ataques detectados, proporcionando visibilidad y cumplimiento.

7. Interfaz de Gestión: Permite a los administradores configurar reglas, monitorear eventos y generar informes.

Flujo de Operación:

1. Un cliente envía una solicitud HTTP/S a la aplicación web.

2. El WAF intercepta la solicitud.

3. Si es HTTPS, el WAF termina la conexión SSL/TLS, descifrando el tráfico.

4. El WAF analiza la solicitud (cabeceras, cuerpo, parámetros, cookies, URL) utilizando su motor de reglas.

5. Si la solicitud coincide con una regla maliciosa o viola una política de seguridad, el WAF puede:

  • * Bloquear la solicitud y enviar una página de error al cliente.
  • * Alertar al administrador.
  • * Registrar el evento.
  • * Inyectar código de seguridad (ej. para prevenir XSS).

6. Si la solicitud es legítima, el WAF la re-cifra (si aplica) y la envía a la aplicación web.

7. La aplicación web procesa la solicitud y devuelve una respuesta.

8. El WAF intercepta la respuesta, la inspecciona (ej. para evitar fuga de datos sensibles o XSS reflejado).

9. Si la respuesta es legítima, el WAF la re-cifra (si aplica) y la envía al cliente.

Modelo de Datos/Comunicación

El WAF opera fundamentalmente en el modelo de comunicación HTTP/S. Su análisis se centra en los siguientes elementos de los datos:

  • Cabeceras HTTP: Examina User-Agent, Referer, Host, Content-Type, Cookie, Authorization, etc., buscando anomalías, datos maliciosos o intentos de evasión.
  • Métodos HTTP: Valida que solo se usen los métodos permitidos (GET, POST, PUT, DELETE, etc.) para rutas específicas.
  • Parámetros de la URL (Query String): Inspecciona los valores enviados en la URL, buscando inyecciones SQL, XSS o path traversal.
  • Cuerpo de la Solicitud (Request Body): Analiza el contenido de POST, PUT (XML, JSON, formularios codificados) en busca de payloads maliciosos.
  • Cookies: Monitorea y protege las cookies de sesión contra manipulación o robo.
  • Respuesta de la Aplicación: Inspecciona el contenido de la respuesta (HTML, JSON, XML) para prevenir la fuga de información sensible, XSS reflejado o ataques de CSRF insertando tokens.

La capacidad de inspeccionar y manipular estos elementos a nivel de aplicación es lo que distingue al WAF de otros dispositivos de seguridad de red. La terminación SSL/TLS es crítica para este modelo, ya que sin descifrar el tráfico, el WAF solo vería datos cifrados y no podría aplicar sus reglas.

Ventajas Clave y Desventajas

Ventajas Clave:

  • Protección Especializada de Capa 7: Mitiga eficazmente el OWASP Top 10 y otros ataques específicos de aplicaciones web que los firewalls de red tradicionales no pueden abordar.
  • Virtual Patching: Permite proteger aplicaciones contra vulnerabilidades conocidas sin modificar el código fuente de la aplicación, lo que es vital para sistemas heredados o cuando los ciclos de parcheo son lentos.
  • Cumplimiento Normativo: Ayuda a cumplir con normativas como PCI DSS, HIPAA, GDPR, que a menudo exigen protección de aplicaciones web.
  • Visibilidad y Monitoreo: Proporciona registros detallados de ataques y tráfico sospechoso, mejorando la postura de seguridad y la capacidad de respuesta.
  • Reglas Personalizables: Permite a las organizaciones adaptar las políticas de seguridad a las necesidades específicas de sus aplicaciones, incluyendo la implementación de modelos de seguridad positivos.
  • Reducción de la Superficie de Ataque: Filtra el tráfico malicioso antes de que llegue a la aplicación, reduciendo la carga en los servidores de la aplicación y potencialmente mejorando el rendimiento general al evitar el procesamiento de solicitudes dañinas.

Desventajas Clave:

  • Falsos Positivos: Una configuración demasiado agresiva puede bloquear tráfico legítimo, afectando la experiencia del usuario y requiriendo un ajuste continuo (tuning).
  • Falsos Negativos: Una configuración deficiente o desactualizada puede permitir que ataques sofisticados pasen desapercibidos.
  • Sobrecarga de Rendimiento (Performance Overhead): La inspección profunda de paquetes, especialmente con la terminación SSL/TLS, puede introducir latencia y consumir recursos de CPU, afectando el rendimiento de la aplicación.
  • Complejidad de Configuración y Mantenimiento: La implementación y el tuning de reglas, especialmente en un modelo de seguridad positivo, requieren personal especializado y un esfuerzo continuo para adaptarse a los cambios en la aplicación y las nuevas amenazas.
  • No es una Panacea: Un WAF no puede proteger contra todos los tipos de ataques, como vulnerabilidades de lógica de negocio (ej. autorización incorrecta entre usuarios legítimos), ataques de día cero (sin firmas conocidas) o fallas en el diseño de la aplicación.
  • Riesgo de Bypass: Un atacante hábil puede intentar evadir las reglas del WAF si no están configuradas correctamente o si el WAF es un producto genérico sin personalización.
  • Costo: Las soluciones WAF empresariales, ya sean de hardware, software o en la nube, pueden ser costosas, especialmente las que ofrecen capacidades avanzadas.

Preguntas de Entrevista sobre WAF (Web Application Firewall)

Pregunta 1: Explica la diferencia fundamental entre un WAF y un IPS (Intrusion Prevention System) o un Firewall de Red tradicional. ¿En qué escenarios es crucial el uso de un WAF sobre los otros?

Respuesta detallada:

La diferencia fundamental radica en la capa del modelo OSI en la que operan y el nivel de inteligencia sobre el tráfico.

  • Firewall de Red Tradicional: Opera en las capas 3 y 4 (red y transporte). Su función principal es controlar el tráfico basándose en direcciones IP de origen/destino, puertos y protocolos. No inspecciona el contenido del paquete más allá de las cabeceras de red y transporte. Su principal objetivo es segmentar la red y restringir el acceso a puertos y servicios.
  • IPS (Intrusion Prevention System): Opera principalmente en las capas 3 a 7, pero su enfoque es más amplio que el de un WAF. Un IPS monitorea el tráfico de red en busca de patrones de ataques conocidos (firmas) o anomalías en el comportamiento de la red. Puede proteger contra una gama más amplia de ataques, incluyendo vulnerabilidades de red, malware, DoS genéricos, pero su comprensión del contexto de una aplicación web HTTP/S es limitada. A menudo, carece de la capacidad de entender la semántica de HTTP/S y los parámetros específicos de la aplicación.
  • WAF (Web Application Firewall): Opera específicamente en la capa 7 (aplicación), con un enfoque en el protocolo HTTP/S. Entiende la semántica de las solicitudes y respuestas HTTP/S, incluyendo cabeceras, métodos, URLs, parámetros, cookies y el cuerpo de la solicitud/respuesta. Esto le permite detectar y mitigar ataques específicos de aplicaciones web como inyección SQL, XSS, manipulación de sesiones, path traversal, etc., que otros firewalls o IPS no pueden detectar porque no "entienden" el contenido de la aplicación.

Escenarios cruciales para un WAF:

El WAF es crucial en cualquier escenario donde la seguridad de las aplicaciones web sea una preocupación primordial. Esto incluye:

  • Protección contra el OWASP Top 10: Los ataques más comunes dirigidos a aplicaciones web (ej., inyección, XSS, broken authentication, broken access control) son el dominio principal de un WAF.
  • Aplicaciones críticas para el negocio: Donde una brecha de seguridad podría tener graves consecuencias financieras, de reputación o regulatorias.
  • Requisitos de cumplimiento: Normativas como PCI DSS, HIPAA o GDPR a menudo exigen medidas específicas para proteger los datos en las aplicaciones web, lo que un WAF puede facilitar enormemente.
  • Virtual Patching: Cuando una aplicación tiene vulnerabilidades conocidas y el ciclo de desarrollo para parchear el código es largo, un WAF puede proporcionar protección inmediata.
  • Protección de APIs: Las APIs web (REST, GraphQL) son esencialmente aplicaciones web sin interfaz de usuario, y un WAF puede protegerlas de ataques similares a los dirigidos a aplicaciones web tradicionales.

Pregunta 2: ¿Cómo un WAF maneja el tráfico SSL/TLS para la inspección de contenido y cuáles son las implicaciones de seguridad y rendimiento de este proceso?

Respuesta detallada:

Para inspeccionar el contenido de una solicitud o respuesta HTTP/S, el WAF debe tener acceso al texto claro (desencriptado). Esto se logra mediante un proceso conocido como Terminación SSL/TLS (o "SSL Offloading").

El proceso es el siguiente:

1. Handshake Inicial: Cuando un cliente inicia una conexión HTTPS con el servidor web (donde el WAF está posicionado como proxy), el WAF intercepta esta conexión y realiza el handshake SSL/TLS con el cliente, actuando como si fuera el servidor web final. Para esto, el WAF debe tener el certificado SSL/TLS del dominio que está protegiendo.

2. Descifrado: Una vez establecida la conexión segura con el cliente, el WAF descifra el tráfico entrante utilizando la clave privada del certificado.

3. Inspección de Contenido: Con el tráfico en texto claro, el WAF puede ahora aplicar todas sus reglas de seguridad (detección de firmas, análisis de anomalías, políticas positivas) a las cabeceras, parámetros, cuerpo y cookies de la solicitud.

4. Re-cifrado (o envío en HTTP):

  • * Si la comunicación entre el WAF y el servidor de la aplicación es también HTTPS, el WAF inicia una nueva conexión SSL/TLS con el servidor de la aplicación, re-cifra el tráfico (potencialmente usando un certificado diferente) y lo envía al servidor.
  • * Si la comunicación entre el WAF y el servidor de la aplicación es HTTP (lo cual es común en arquitecturas internas seguras), el WAF envía la solicitud en texto claro al servidor.

5. Proceso Inverso para la Respuesta: Cuando la aplicación responde, el WAF intercepta la respuesta, la inspecciona (si es necesario), y luego la cifra usando el certificado del cliente antes de enviarla de vuelta al cliente.

Implicaciones de Seguridad:

  • Punto de Confianza: El WAF se convierte en un punto de confianza crítico. Si el WAF es comprometido, la seguridad de las comunicaciones cifradas se ve comprometida.
  • Gestión de Claves: La clave privada del certificado SSL/TLS debe estar en el WAF, lo que añade un punto más para la protección de claves sensibles.
  • Ataques de "Man-in-the-Middle": Técnicamente, el WAF está realizando un ataque de "Man-in-the-Middle" controlado. Es crucial que los certificados estén correctamente gestionados para evitar que actores maliciosos puedan hacer lo mismo.
  • Cumplimiento: Algunas regulaciones pueden tener requisitos específicos sobre dónde y cómo se termina SSL/TLS.

Implicaciones de Rendimiento:

  • Sobrecarga Computacional: El cifrado y descifrado de cada solicitud y respuesta son operaciones intensivas en CPU. Esto añade una sobrecarga significativa al WAF, que debe tener suficiente capacidad para manejar el volumen de tráfico.
  • Latencia: El proceso de terminación, inspección y re-cifrado introduce una pequeña cantidad de latencia adicional en cada solicitud. Aunque a menudo es mínima, en aplicaciones de baja latencia crítica puede ser un factor.
  • Escalabilidad: La capacidad del WAF para manejar el tráfico SSL/TLS es un factor clave en su escalabilidad. Las soluciones WAF modernas a menudo utilizan hardware especializado (ASICs) para acelerar estas operaciones.

Pregunta 3: Describe los modelos de seguridad "lista blanca" (Positive Security Model) y "lista negra" (Negative Security Model) en WAFs. ¿Cuál es generalmente más seguro y por qué, y qué desafíos presenta cada uno?

Respuesta detallada:

Ambos modelos son enfoques para definir las reglas de seguridad dentro de un WAF.

1. Modelo de Seguridad de "Lista Negra" (Negative Security Model):

  • Concepto: Este modelo funciona permitiendo por defecto todo el tráfico, a menos que coincida con una firma o patrón de ataque conocido. Es decir, se define lo que está prohibido*.
  • * Funcionamiento: El WAF mantiene una base de datos de firmas que representan ataques conocidos (ej., patrones de inyección SQL, scripts XSS, encabezados maliciosos). Cualquier solicitud que coincida con una de estas firmas es bloqueada o marcada.
  • * Ventajas:
  • * Fácil de implementar y desplegar inicialmente.
  • * Requiere menos conocimiento de la aplicación protegida.
  • * Las reglas se pueden actualizar automáticamente para proteger contra nuevas amenazas conocidas.
  • * Desventajas:
  • * Vulnerable a ataques desconocidos (Zero-Day): Si un ataque no tiene una firma existente, puede pasar desapercibido.
  • * Ataques de Evasión: Los atacantes pueden intentar "mutar" sus ataques para que no coincidan con las firmas conocidas (ej., codificación múltiple, técnicas de ofuscación).
  • * Puede generar más falsos negativos (ataques que pasan).

2. Modelo de Seguridad de "Lista Blanca" (Positive Security Model):

  • Concepto: Este modelo funciona denegando por defecto todo el tráfico, a menos que coincida con un patrón de comportamiento o estructura permitida explícitamente. Es decir, se define lo que está permitido*.
  • * Funcionamiento: El WAF aprende o se configura para conocer la estructura esperada de las solicitudes legítimas para una aplicación: URLs permitidas, métodos HTTP, tipos de datos en parámetros, longitud máxima, caracteres especiales, etc. Cualquier solicitud que no se ajuste a este perfil "normal" o "permitido" es bloqueada.
  • * Ventajas:
  • * Más seguro contra ataques desconocidos: Como solo permite lo explícitamente conocido, es mucho más resistente a ataques de día cero y técnicas de evasión, ya que cualquier cosa fuera del perfil esperado será bloqueada.
  • * Genera menos falsos negativos.
  • * Desventajas:
  • * Extremadamente complejo de implementar y mantener: Requiere un conocimiento profundo de la aplicación, sus entradas y salidas esperadas.
  • * Alto riesgo de falsos positivos: Pequeños cambios en la aplicación o nuevos casos de uso pueden generar bloqueos de tráfico legítimo si las reglas de la lista blanca no se actualizan continuamente.
  • * Proceso de aprendizaje: El WAF debe "aprender" el comportamiento normal de la aplicación, lo que lleva tiempo y puede ser volátil en entornos dinámicos.

¿Cuál es generalmente más seguro y por qué?

El Modelo de Seguridad de "Lista Blanca" es generalmente más seguro porque su premisa fundamental es que todo lo que no está explícitamente permitido, está prohibido. Esto lo hace intrínsecamente más robusto contra ataques novedosos o variantes de ataques conocidos, ya que no depende de tener una firma específica para cada amenaza. Es como cerrar todas las puertas y ventanas y solo abrir una pequeña mirilla para las interacciones esperadas.

Sin embargo, debido a su complejidad y la alta probabilidad de falsos positivos, muchos WAFs en producción utilizan una combinación de ambos modelos, con un predominio de la lista negra para una implementación más ágil y algunas reglas de lista blanca muy específicas para puntos críticos de la aplicación (ej. campos de login, APIs sensibles). La madurez y el contexto operativo de la organización suelen dictar el equilibrio entre ambos.

Pregunta 4: En un entorno de microservicios, ¿dónde posicionarías un WAF y cuáles serían las consideraciones clave de implementación en comparación con una arquitectura monolítica tradicional?

Respuesta detallada:

En un entorno de microservicios, existen varias opciones para posicionar un WAF, y la elección depende de la granularidad de protección deseada, la arquitectura de red y las preocupaciones de rendimiento.

Posicionamiento:

1. WAF en el Edge/Perímetro (delante del API Gateway/Load Balancer): Esta es la posición más común y a menudo la más práctica.

  • * Descripción: El WAF se ubica globalmente o regionalmente, antes de que el tráfico llegue al API Gateway, balanceador de carga o ingress controller (en Kubernetes).
  • * Ventajas: Protege todos los servicios expuestos, centraliza la seguridad, reduce la carga en los microservicios individuales, puede gestionar certificados SSL/TLS para todo el ecosistema. Es similar a cómo se desplegaría en un monolito, protegiendo todo el tráfico externo.
  • * Consideraciones: No protege el tráfico entre microservicios (east-west) si no se enruta a través de él. Si el API Gateway ya ofrece algunas funciones de seguridad (ej. rate limiting, autenticación), puede haber redundancia o conflicto.

2. WAF Integrado en el API Gateway:

  • * Descripción: Algunos API Gateways (como AWS API Gateway, Azure API Management, Kong, Apigee) tienen capacidades de WAF integradas o permiten la integración con servicios WAF (ej. AWS WAF con API Gateway).
  • * Ventajas: Seguridad más cercana a la lógica de negocio expuesta por el API Gateway, configuración simplificada si el WAF es parte del ecosistema del Gateway, puede aplicar políticas más granulares por API o ruta.
  • * Consideraciones: Depende de las capacidades específicas del API Gateway. No todos los gateways ofrecen un WAF completo. Puede añadir carga al gateway.

3. WAF por Microservicio (Sidecar/Embedded):

  • * Descripción: Cada microservicio o un grupo de ellos tiene su propio WAF, quizás como un sidecar en un Service Mesh (ej. con Envoy y un filtro WAF como ModSecurity) o como un componente integrado.
  • * Ventajas: Protección granular por cada servicio, incluso para tráfico east-west. Ideal para proteger servicios altamente sensibles. Permite políticas de seguridad muy específicas para cada microservicio.
  • * Consideraciones:
  • * Complejidad y Mantenimiento: Muy costoso y complejo de configurar, desplegar y mantener un WAF para cada servicio.
  • * Rendimiento: Alta sobrecarga de recursos (CPU, memoria) y latencia adicional en cada salto si el WAF es un proxy local.
  • * Consistencia: Dificil asegurar que todas las instancias de WAF estén actualizadas y configuradas de manera consistente.

Consideraciones Clave de Implementación en Comparación con Monolitos:

  • Tráfico Este-Oeste vs. Norte-Sur: En un monolito, el tráfico es predominantemente norte-sur (cliente-servidor). En microservicios, hay una cantidad significativa de tráfico este-oeste (servicio-a-servicio). Un WAF perimetral solo protege el norte-sur. Para el este-oeste, se necesitan soluciones como Service Meshes con políticas de seguridad, autenticación mutua TLS (mTLS), y quizás filtros WAF ligeros.
  • Gestión de APIs: Los microservicios a menudo exponen APIs en lugar de interfaces de usuario tradicionales. Los WAF deben ser capaces de entender y proteger formatos como JSON y GraphQL, y no solo HTML.
  • Despliegue y Automatización (DevSecOps): Con docenas o cientos de microservicios, la configuración manual del WAF es inviable. Se requiere "WAF as Code" e integración profunda con pipelines CI/CD para automatizar la gestión de reglas y políticas.
  • Rendimiento y Escalabilidad: El overhead de un WAF es más pronunciado en un entorno distribuido. Se debe asegurar que el WAF pueda escalar horizontalmente con el crecimiento de los microservicios y no se convierta en un cuello de botella.
  • Observabilidad: La agregación de logs y métricas de seguridad de múltiples WAFs distribuidos es esencial para tener una visión holística de la postura de seguridad.

En general, la estrategia más equilibrada suele ser un WAF perimetral (probablemente en la nube o como parte de un CDN/API Gateway global) para proteger el tráfico norte-sur y un Service Mesh con mTLS y políticas de autorización entre servicios para el tráfico este-oeste.

Pregunta 5: ¿Qué rol juega el "virtual patching" en la estrategia de seguridad de aplicaciones y cómo se implementa con un WAF?

Respuesta detallada:

El "virtual patching" (también conocido como parcheo virtual o escudo de vulnerabilidades) es una estrategia de seguridad que permite proteger una aplicación web de una vulnerabilidad conocida sin modificar el código fuente de la aplicación misma. En lugar de aplicar un parche directamente al software vulnerable, se implementa una medida compensatoria a nivel de WAF que intercepta y bloquea los intentos de explotar esa vulnerabilidad.

Rol en la Estrategia de Seguridad:

El virtual patching es crucial en los siguientes escenarios:

  • Tiempo de Respuesta Reducido: Permite una protección inmediata contra vulnerabilidades recién descubiertas (zero-day o N-day) antes de que un parche oficial esté disponible y pueda ser desplegado.
  • Sistemas Legacy/Heredados: Protege aplicaciones antiguas o descontinuadas que ya no reciben soporte o parches del fabricante, o para las cuales el código fuente es inaccesible o demasiado costoso de modificar.
  • Ciclos de Despliegue Lentos: En organizaciones con ciclos de desarrollo y despliegue de software prolongados, el virtual patching proporciona una capa de seguridad provisional hasta que la corrección de código se pueda implementar y probar completamente.
  • Reducción del Riesgo: Minimiza la ventana de exposición a vulnerabilidades críticas, reduciendo el riesgo general para la organización.
  • Costo-Efectividad: A menudo es más rápido y menos costoso implementar un parche virtual que realizar un desarrollo, pruebas y despliegue de un parche de código completo, especialmente para vulnerabilidades no críticas o temporales.

Implementación con un WAF:

Un WAF es la herramienta principal para implementar el virtual patching debido a su capacidad para inspeccionar y manipular el tráfico de la capa 7. La implementación sigue estos pasos:

1. Identificación de la Vulnerabilidad: Se detecta una vulnerabilidad en la aplicación (mediante escaneos de seguridad, pruebas de penetración, análisis de código o alertas de seguridad).

2. Análisis de la Explotación: Se entiende cómo se explota la vulnerabilidad (ej., qué parámetros se usan, qué patrones de entrada se envían, qué tipo de respuesta se espera).

3. Creación de la Regla del WAF: Se diseña una regla específica para el WAF que detecte y bloquee los patrones de tráfico asociados con la explotación de esa vulnerabilidad. Ejemplos:

  • * Inyección SQL: Bloquear entradas que contengan patrones como ' OR 1=1-- en campos específicos.
  • * XSS: Bloquear entradas con tags
