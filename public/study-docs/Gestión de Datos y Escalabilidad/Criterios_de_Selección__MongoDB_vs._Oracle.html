Criterios de Selección: MongoDB vs. Oracle

El "Criterio de Selección: MongoDB vs. Oracle" no es un patrón de arquitectura de software en el sentido tradicional de patrones estructurales (como Microservicios, Capas, etc.), sino más bien un patrón de decisión arquitectónica. Representa el proceso de evaluar y elegir la tecnología de base de datos más adecuada (en este caso, entre MongoDB y Oracle) basándose en los requisitos específicos del proyecto y del negocio.

Este proceso de decisión es fundamental en la arquitectura de software, ya que la base de datos es un componente central que afecta el rendimiento, la escalabilidad, la flexibilidad y el costo de una aplicación.

---

Criterios de Selección: MongoDB vs. Oracle

Conceptos Principales

#### MongoDB

  • Tipo: Base de datos NoSQL, orientada a documentos.
  • Modelo de Datos: Almacena datos en documentos BSON (Binary JSON), que pueden anidarse y contener arrays, ofreciendo una estructura muy flexible.
  • Esquema: Sin esquema (schemaless) o esquema flexible. Los documentos en una colección no necesitan tener la misma estructura.
  • Escalabilidad: Diseñada para escalabilidad horizontal (sharding), distribuyendo los datos entre múltiples servidores.
  • Consistencia: Ofrece una consistencia eventual por defecto, aunque configurable para mayor consistencia en ciertas operaciones.
  • Uso Ideal: Aplicaciones web y móviles modernas, IoT, análisis de datos en tiempo real, catálogos de productos, sistemas con datos semiestructurados o no estructurados y requisitos de alta disponibilidad.

#### Oracle Database

  • Tipo: Sistema de Gestión de Bases de Datos Relacionales (RDBMS).
  • Modelo de Datos: Almacena datos en tablas con filas y columnas, siguiendo un esquema predefinido y estricto. Utiliza SQL para la manipulación de datos.
  • Esquema: Rígido y predefinido. Los cambios en el esquema requieren migraciones cuidadosas.
  • Escalabilidad: Tradicionalmente escalabilidad vertical (mejor hardware), aunque ofrece soluciones de alta disponibilidad y escalabilidad horizontal como Real Application Clusters (RAC).
  • Consistencia: Garantiza la consistencia fuerte y el cumplimiento de las propiedades ACID (Atomicidad, Consistencia, Aislamiento, Durabilidad) para todas las transacciones.
  • Uso Ideal: Sistemas transaccionales críticos (OLTP), aplicaciones empresariales legacy, sistemas financieros, gestión de inventarios, donde la integridad de los datos y la consistencia son primordiales.

Ventajas de MongoDB

  • Flexibilidad de Esquema: Permite un desarrollo ágil y la adaptación a requisitos cambiantes sin complejas migraciones de esquema.
  • Escalabilidad Horizontal: Muy fácil de escalar horizontalmente para manejar grandes volúmenes de datos y alto tráfico.
  • Rendimiento: Alta velocidad para operaciones de lectura/escritura en documentos, especialmente con datos anidados.
  • Orientado a Objetos: El modelo de documentos se alinea bien con la programación orientada a objetos, simplificando el mapeo de objetos en la aplicación a la base de datos.
  • Desarrollo Rápido: Ideal para prototipos y desarrollo iterativo debido a su flexibilidad.
  • Costo: Versión Community Edition es open-source, reduciendo costos de licencia iniciales.

Desventajas de MongoDB

  • Consistencia ACID Menos Estricta: Aunque ha mejorado, no ofrece las mismas garantías ACID de forma predeterminada que un RDBMS tradicional.
  • Consultas Complejas (JOINs): No maneja JOINs relacionales de forma nativa. Las relaciones entre documentos suelen manejarse a nivel de aplicación o mediante desnormalización, lo que puede aumentar la complejidad o el tamaño de los datos.
  • Madurez y Herramientas: Aunque ha crecido, su ecosistema y herramientas no son tan maduros ni tan amplios como los de Oracle.
  • Sobrecarga de Almacenamiento: La desnormalización para optimizar consultas puede llevar a la duplicación de datos y mayor consumo de almacenamiento.
  • Seguridad: Requiere una configuración cuidadosa y profunda para asegurar la base de datos.

Ventajas de Oracle Database

  • Consistencia ACID Fuerte: Garantiza la máxima integridad y fiabilidad de los datos, crucial para transacciones críticas.
  • Madurez y Robustez: Décadas de desarrollo, es una solución extremadamente estable y probada en entornos empresariales críticos.
  • Consultas SQL Potentes: SQL es un lenguaje estandarizado y muy potente para consultas complejas, agregaciones y análisis de datos relacionales.
  • Soporte Empresarial: Amplio soporte, documentación y un ecosistema de herramientas y profesionales (DBAs) experimentados.
  • Seguridad Avanzada: Ofrece características de seguridad muy sofisticadas, auditoría y cumplimiento normativo.
  • Ecosistema Extenso: Integración con una amplia gama de herramientas de BI, ETL y otras aplicaciones empresariales.

Desventajas de Oracle Database

  • Costo Elevado: Licencias, hardware y mantenimiento son significativamente caros, lo que puede ser una barrera para startups o proyectos con presupuestos limitados.
  • Rigidez de Esquema: Los cambios en el esquema requieren un proceso formal y a menudo disruptivo.
  • Escalabilidad Horizontal: Más compleja y costosa de implementar que en NoSQL, a menudo requiriendo soluciones como RAC.
  • Administración Compleja: Requiere DBAs altamente especializados y un esfuerzo considerable en administración y optimización.
  • Manejo de Datos No Estructurados: Menos eficiente y natural para almacenar datos JSON o XML sin un esquema fijo, aunque ha incorporado funcionalidades para ello.
  • Desarrollo Más Lento: La rigidez del esquema y la necesidad de definir tablas de antemano pueden ralentizar el ciclo de desarrollo en fases iniciales.

---

Cuándo Elegir MongoDB

  • Datos: Semi-estructurados, no estructurados o con estructura cambiante.
  • Escalabilidad: Necesidad de escalar horizontalmente de forma rápida y sencilla para manejar grandes volúmenes de datos y usuarios.
  • Desarrollo: Metodologías ágiles, prototipado rápido, alta iteración.
  • Modelo de Datos: Cuando los datos se mapean naturalmente a documentos (ej. objetos JSON en una API REST).
  • Costo: Proyectos con presupuestos ajustados para licencias o que prefieren soluciones open-source.
  • Disponibilidad: Alta disponibilidad y tolerancia a fallos requeridas a través de réplicas.

Cuándo Elegir Oracle

  • Datos: Estructurados, con relaciones complejas y estrictas.
  • Consistencia: Requisitos estrictos de integridad de datos y transacciones ACID.
  • Seguridad: Necesidad de seguridad robusta, auditoría y cumplimiento normativo.
  • Escalabilidad: Cuando la escalabilidad vertical es suficiente o se puede justificar la complejidad de RAC para escalabilidad horizontal.
  • Ecosistema: Proyectos que ya están invertidos en el ecosistema Oracle o requieren su amplio conjunto de herramientas empresariales.
  • Madurez: Cuando la estabilidad y la fiabilidad a largo plazo son críticas para el negocio.

Conclusión

La elección entre MongoDB y Oracle no es una cuestión de cuál es "mejor" en general, sino de cuál es "más adecuado" para los requisitos específicos del proyecto. Un arquitecto de software debe considerar cuidadosamente los criterios de datos, escalabilidad, consistencia, costo, flexibilidad y madurez del ecosistema para tomar una decisión informada que optimice el rendimiento, la mantenibilidad y la vida útil de la aplicación. En algunos casos, incluso una arquitectura híbrida podría ser la solución, utilizando ambas bases de datos para diferentes partes de la aplicación.

Ejemplo de Aplicación Real

Aquí tienes un ejemplo detallado de la aplicación del concepto "Criterios de Selección: MongoDB vs. Oracle" en un escenario empresarial real.

---

Criterios de Selección: MongoDB vs. Oracle - Estudio de Caso

Nombre de la Empresa: AuraFlow Dynamics

Sector: Logística y Gestión de Cadena de Suministro (Supply Chain Management - SCM)

Producto Principal: Plataforma SaaS para optimización de rutas, monitoreo de flotas en tiempo real, gestión de inventarios distribuidos y análisis predictivo de la cadena de suministro para grandes minoristas y empresas de manufactura.

1. El Problema Empresarial

AuraFlow Dynamics había crecido exponencialmente en los últimos cinco años. Su plataforma original se construyó sobre una base de datos Oracle Database Enterprise Edition, que había servido bien para las operaciones transaccionales críticas (órdenes de envío, manifiestos de carga, facturación).

Sin embargo, la empresa enfrentaba varios desafíos apremiantes:

  • Explosión de Datos Variados:
  • * Datos IoT: Millones de telemetrías por minuto de vehículos (GPS, velocidad, temperatura, consumo de combustible, estado del motor).
  • * Datos de Sensores de Inventario: Temperaturas, humedad, ubicación, estado de los productos en almacenes y tránsito.
  • * Documentos No Estructurados: Contratos de proveedores, notas de incidentes, fotos de daños, documentos de aduanas, descripciones detalladas de productos y embalajes con formatos variables.
  • * Datos de Redes Sociales/Noticias: Análisis de sentimiento y menciones para evaluar riesgos geopolíticos o climáticos que podrían afectar la cadena de suministro.
  • Escalabilidad y Rendimiento: La base de datos Oracle existente se estaba volviendo un cuello de botella para:
  • * Ingestar y procesar la inmensa cantidad de datos IoT en tiempo real.
  • * Ejecutar análisis predictivos complejos que requerían escanear grandes volúmenes de datos históricos de telemetría y eventos.
  • * Actualizar dinámicamente los mapas y rutas con información de tráfico y clima en tiempo real.
  • * La latencia estaba aumentando, afectando la capacidad de los clientes para tomar decisiones rápidas.
  • Flexibilidad del Esquema: Añadir nuevas funcionalidades (por ejemplo, nuevos tipos de sensores, integrar datos de nuevos socios con esquemas diferentes) requería cambios de esquema complejos y costosos en Oracle, ralentizando la innovación.
  • Costos Crecientes: Las licencias de Oracle Enterprise Edition y los costos de infraestructura para escalar verticalmente (servidores más potentes, almacenamiento SAN) estaban disparándose a un ritmo insostenible.
  • Complejidad del Desarrollo: La necesidad de normalizar todos los datos en un esquema relacional rígido estaba obstaculizando la agilidad de los equipos de desarrollo para experimentar con nuevos modelos de análisis y tipos de datos.

2. Implementación del Concepto: Criterios de Selección

AuraFlow Dynamics decidió implementar una estrategia de "data-tiering" (tiering de datos) y eligió un comité de arquitectura para evaluar la viabilidad de incorporar una base de datos NoSQL, específicamente MongoDB, junto con su infraestructura Oracle existente.

Los criterios de selección se definieron y ponderaron de la siguiente manera:

#### Criterios de Evaluación Clave:

1. Tipo de Datos y Modelo de Datos (Peso: 25%)

  • * Oracle: Excelente para datos altamente estructurados, transaccionales, con relaciones complejas y estrictas reglas de integridad (ej. órdenes, facturación, datos maestros de clientes y proveedores).
  • * MongoDB: Ideal para datos semi-estructurados, no estructurados, con esquemas flexibles y anidados (ej. logs IoT, datos de sensores, documentos de incidentes, perfiles de usuarios de la plataforma).

2. Escalabilidad y Rendimiento (Peso: 20%)

  • * Oracle: Fuerte escalabilidad vertical (RAC, servidores potentes), pero la escalabilidad horizontal para volúmenes masivos de datos dispares es compleja y costosa. Rendimiento excelente para consultas OLTP complejas.
  • * MongoDB: Diseñado para escalabilidad horizontal (sharding) desde el principio, permitiendo manejar petabytes de datos y millones de operaciones por segundo con un rendimiento predecible en clústeres distribuidos. Ideal para ingesta masiva de datos y consultas de rango/campo en grandes volúmenes.

3. Flexibilidad del Esquema y Agilidad de Desarrollo (Peso: 15%)

  • * Oracle: Requiere un esquema predefinido y cambios de esquema pueden ser costosos y requerir downtime. Menos ágil para prototipado rápido con datos cambiantes.
  • * MongoDB: Modelo de documento sin esquema (schema-less) que permite a los desarrolladores iterar rápidamente, añadir nuevos campos o estructuras de datos sin afectar a los datos existentes. Facilita la integración con nuevas fuentes de datos.

4. Consistencia y Transaccionalidad (ACID) (Peso: 15%)

  • * Oracle: Cumplimiento total de ACID (Atomicidad, Consistencia, Aislamiento, Durabilidad) para transacciones complejas y críticas, garantizando la integridad de los datos.
  • MongoDB: Ofrece transacciones multi-documento a partir de la versión 4.0, proporcionando garantías ACID para un subconjunto de operaciones, pero su modelo nativo es más orientado a la disponibilidad y particionamiento, con consistencia eventual por defecto en réplicas. Adecuado para datos donde la latencia es más crítica que la consistencia fuerte instantánea* a nivel de sistema distribuido.

5. Costo Total de Propiedad (TCO) (Peso: 10%)

  • * Oracle: Altos costos de licencia y soporte, especialmente para Enterprise Edition y escalar a grandes volúmenes. Requiere DBAs especializados.
  • * MongoDB: La Community Edition es de código abierto. MongoDB Atlas (Cloud) y Enterprise Edition ofrecen opciones de soporte y características avanzadas, pero suelen ser más económicos a gran escala que Oracle para cargas de trabajo comparables.

6. Ecosistema, Herramientas y Experiencia del Equipo (Peso: 10%)

  • * Oracle: Ecosistema maduro, amplia gama de herramientas de administración, ETL y BI. El equipo interno tiene experiencia significativa en Oracle.
  • * MongoDB: Ecosistema robusto para desarrollo web y microservicios, integración con herramientas de análisis y BI modernas. La curva de aprendizaje es más suave para desarrolladores familiarizados con JSON.

7. Seguridad (Peso: 5%)

  • * Ambos: Ofrecen características de seguridad robustas (cifrado en tránsito y en reposo, autenticación, autorización basada en roles). Oracle tiene una historia más larga en seguridad empresarial.

#### Decisión Arquitectónica y Estrategia Híbrida:

Basándose en esta evaluación, AuraFlow Dynamics decidió implementar una arquitectura de base de datos híbrida o políglota:

  • Oracle Database Enterprise Edition:
  • * Rol: Base de datos principal para todos los datos transaccionales críticos que requieren estrictas garantías ACID: órdenes de envío, manifiestos de carga, información de facturación, datos maestros de clientes y proveedores, información de pago.
  • * Razones: La solidez de Oracle para transacciones complejas, su madurez y la experiencia del equipo en su administración para la integridad crítica del negocio.
  • MongoDB Atlas (Cloud Managed Service):
  • * Rol: Base de datos para la ingesta, almacenamiento y análisis de datos de alto volumen y variabilidad: telemetría IoT de vehículos y sensores, logs de eventos, documentos de incidentes, datos de tráfico y clima en tiempo real, perfiles de usuario enriquecidos, catálogos de productos flexibles, datos de análisis predictivo.
  • * Razones: Su capacidad de escalabilidad horizontal (sharding), flexibilidad del esquema, rendimiento para escrituras masivas y lecturas rápidas en grandes volúmenes de datos, y menores costos operativos a escala a través de Atlas.

Flujo de Datos y Conectividad:

  • Se implementó una capa de integración usando un Message Broker (Kafka) para desacoplar los sistemas.
  • Los datos de telemetría y sensores se ingestarían directamente en MongoDB a través de Kafka.
  • Los eventos de cambio en Oracle (ej., una orden de envío cambia de estado) se publicarían en Kafka para que MongoDB pudiera actualizar los perfiles de usuario o los estados de envío no críticos de forma asíncrona.
  • Los resultados de análisis predictivos generados por algoritmos que operan sobre datos en MongoDB podrían ser "resumidos" y enviados de vuelta a Oracle para referencia en dashboards gerenciales si era necesario, o directamente consumidos por microservicios desde MongoDB.

3. Resultados y Beneficios Obtenidos

La implementación de esta estrategia híbrida trajo consigo beneficios significativos para AuraFlow Dynamics:

1. Escalabilidad Masiva y Rendimiento Superior:

  • * La plataforma pudo ingestar y procesar miles de millones de puntos de datos IoT diarios sin degradación del rendimiento.
  • * Las consultas analíticas complejas sobre datos históricos masivos, que antes tomaban minutos, ahora se completan en segundos, permitiendo análisis predictivos casi en tiempo real.
  • * Las actualizaciones de rutas y la visualización de flotas en vivo son fluidas y altamente responsivas.

2. Agilidad de Desarrollo Acelerada:

  • * Los equipos de desarrollo pueden lanzar nuevas características que integran nuevos tipos de sensores o fuentes de datos en semanas en lugar de meses, gracias a la flexibilidad del esquema de MongoDB.
  • * Esto permitió a AuraFlow Dynamics innovar más rápidamente y responder a las cambiantes necesidades del mercado y de sus clientes.

3. Optimización de Costos:

  • * Se evitó la necesidad de realizar costosas actualizaciones de licencias y hardware para escalar Oracle para todas las cargas de trabajo de datos variados y de alto volumen.
  • * Los costos operativos generales se redujeron significativamente al usar MongoDB Atlas, que ofrece un modelo de pago por uso y administración simplificada.

4. Resiliencia y Disponibilidad Mejoradas:

  • * Al separar las cargas de trabajo, un problema en la ingesta de datos IoT (MongoDB) no afectaría las operaciones transaccionales críticas de la empresa (Oracle), aumentando la resiliencia general del sistema.

5. Mejora en la Toma de Decisiones del Cliente:

  • * Los clientes de AuraFlow Dynamics ahora tienen acceso a información en tiempo real y análisis predictivos más precisos, lo que les permite optimizar sus cadenas de suministro, reducir costos operativos y mejorar la satisfacción de sus propios clientes.

En resumen, la aplicación rigurosa de criterios de selección de bases de datos permitió a AuraFlow Dynamics elegir la herramienta adecuada para cada trabajo, transformando su arquitectura de datos de un cuello de botella monolítico a un motor de innovación ágil y escalable.

Preguntas de Entrevista

En un escenario de microservicios con un alto volumen de datos no estructurados y requisitos de escalabilidad horizontal extrema, ¿qué base de datos recomendaría y por qué? ¿Qué consideraciones operativas clave diferencian a MongoDB de Oracle en este contexto?

Para microservicios con alto volumen de datos no estructurados y escalabilidad horizontal extrema, MongoDB es la opción preferida. Su modelo de datos de documentos permite flexibilidad de esquema, ideal para datos cambiantes y diversos, y su arquitectura distribuida con sharding nativo facilita la escalabilidad horizontal masiva sin complejidad excesiva. Operativamente, MongoDB ofrece una gestión más sencilla de la replicación y distribución de datos a través de clústeres de sharding, lo que reduce la carga del DBA en comparación con intentar escalar Oracle de manera similar para datos no estructurados. Oracle, aunque escalable, requiere soluciones más complejas (RAC, particionamiento, sharding manual o con GoldenGate) para lograr un nivel comparable de escalabilidad horizontal para datos no estructurados, y su modelo relacional impondría una rigidez innecesaria.

Un cliente necesita una base de datos para una aplicación bancaria transaccional con estrictos requisitos ACID y reportes complejos que involucran joins en múltiples tablas. Los datos son altamente relacionales y la consistencia inmediata es crítica. ¿Cómo justificaría la elección de Oracle sobre MongoDB en esta situación?

En un escenario bancario con requisitos ACID estrictos, datos altamente relacionales y transacciones complejas, Oracle es la elección indiscutible. La justificación radica en su madurez y robustez como sistema de gestión de bases de datos relacional (RDBMS), que garantiza la atomicidad, consistencia, aislamiento y durabilidad (ACID) en todas las transacciones. Oracle ofrece un modelo de datos tabular con claves primarias y foráneas que imponen integridad referencial, vital para la consistencia de los datos bancarios. Además, su lenguaje SQL está optimizado para consultas complejas que involucran joins entre múltiples tablas, permitiendo reportes sofisticados. MongoDB, al ser una base de datos NoSQL basada en documentos, prioriza la flexibilidad y la escalabilidad horizontal sobre la consistencia transaccional fuerte en todas las operaciones distribuidas, y no está diseñado para manejar joins complejos o garantizar la integridad referencial de forma nativa a nivel de esquema, lo que la hace inadecuada para este caso de uso.

Imagine un proyecto de migración donde un sistema legacy basado en Oracle necesita integrar un nuevo módulo que gestionará un catálogo de productos con atributos variables y en constante evolución, con un alto volumen de lecturas y escrituras. ¿Qué enfoque adoptaría para el nuevo módulo y cómo gestionaría la interacción con el sistema Oracle existente?

Para el nuevo módulo de catálogo de productos con atributos variables y evolución constante, adoptaría un enfoque políglota, utilizando MongoDB. Su modelo de documentos es ideal para la naturaleza cambiante y semi-estructurada de los atributos de productos, permitiendo agregar o modificar campos sin afectar el esquema de la base de datos subyacente. Para gestionar la interacción con el sistema Oracle existente, implementaría un patrón de 'base de datos para cada servicio' donde el nuevo módulo de catálogo estaría acoplado a MongoDB. La integración con el sistema legacy de Oracle se realizaría a través de APIs bien definidas o un patrón de publicación/suscripción. Por ejemplo, si se necesita sincronizar datos críticos de productos (ej. ID de producto, precio base) entre ambos, se podría usar un sistema de mensajería (como Kafka) o un ETL ligero para enviar actualizaciones desde MongoDB a Oracle (o viceversa, si Oracle sigue siendo la fuente de verdad para ciertos aspectos) solo para los campos estrictamente necesarios para el sistema legacy, evitando replicar la complejidad del catálogo dinámico en Oracle.

Discuta el impacto de la 'flexibilidad de esquema' de MongoDB versus la 'rigidez de esquema' de Oracle en el ciclo de vida de desarrollo de software, específicamente en términos de velocidad de iteración y gestión de cambios. Proporcione un ejemplo donde esta diferencia sea crítica.

La flexibilidad de esquema de MongoDB (schema-less) permite a los desarrolladores iterar rápidamente, agregando o modificando campos en los documentos sin necesidad de migraciones de esquema o downtime de la base de datos. Esto acelera el desarrollo, especialmente en etapas iniciales o en entornos ágiles con requisitos cambiantes. La rigidez de esquema de Oracle, por otro lado, requiere que cualquier cambio en la estructura de la tabla (ej. añadir una columna) implique un script DDL, pruebas de regresión y a menudo un período de mantenimiento, ralentizando el ciclo de desarrollo. Un ejemplo crítico es el desarrollo de una nueva característica para una aplicación móvil donde los requisitos de datos están evolucionando rápidamente (ej. nuevos tipos de interacción del usuario, datos de telemetría). Con MongoDB, los desarrolladores pueden empezar a almacenar nuevos datos inmediatamente. Con Oracle, cada ajuste en el modelo de datos requeriría una planificación y ejecución de migración de esquema, lo que podría retrasar la entrega de la característica o dificultar la experimentación rápida con nuevos modelos de datos.

Explique cómo las consideraciones de licenciamiento y el soporte empresarial difieren significativamente entre MongoDB y Oracle, y cómo estos factores podrían influir en la decisión de una gran empresa con un presupuesto considerable pero también con una aversión al riesgo.

Las consideraciones de licenciamiento y soporte difieren drásticamente. Oracle es conocido por su modelo de licenciamiento comercial complejo y costoso, basado en procesadores, núcleos o usuarios, con tarifas significativas para características avanzadas (RAC, particionamiento) y un soporte empresarial de alto nivel inherente al contrato. Esto representa un coste inicial y recurrente considerable. MongoDB ofrece una versión Community Edition de código abierto gratuita, y una versión Enterprise Advanced con características de seguridad, gestión y rendimiento adicionales, bajo un modelo de suscripción anual, que es generalmente más predecible y a menudo más económico que Oracle. Para una gran empresa con presupuesto considerable pero aversión al riesgo, Oracle ofrece un soporte empresarial y una red de socios establecidos a nivel global, con una trayectoria probada en entornos críticos, lo que reduce el riesgo percibido en cuanto a soporte y compatibilidad. Sin embargo, los costes de licenciamiento pueden escalar desproporcionadamente. MongoDB Enterprise Advanced ofrece un soporte robusto, pero la percepción de riesgo podría ser mayor si la empresa no está familiarizada con el ecosistema NoSQL. La decisión dependería de si la empresa valora más la previsibilidad y el menor coste operativo a largo plazo (MongoDB, aceptando un riesgo percibido potencialmente mayor en el soporte de una tecnología relativamente más nueva para sistemas críticos) o la seguridad y la tradición de un proveedor consolidado (Oracle, aceptando costes más altos y menos flexibilidad de licenciamiento).
